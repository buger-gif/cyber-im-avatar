## v0.7.1：会话落对绑定工作区 + 起草不再自管模型配置

### 现场（用户报的）

「示例对象 E」（飞书单聊，绑 `~/Desktop/业务工作区`）
收到消息后只发出 ack 话术「在的，这个我确认下再答复你。」，正式回复一直没出来；
且按设计该落在 业务工作区 工作区的 DSH 会话，在那个工作区里根本看不见。

### 根因（两条）

1. **会话跨工作区沿用被 DSH 拒**：DSH 的会话按工作区落盘
   （`~/.dsh/sessions/<工作区slug>/<session-id>`）。该 chat 的 `dsh_session`
   是 `session-****`，落盘在 `<默认工作区slug>/`
   （绑定工作区之前建的）。之后每轮起草都带 `--session-id` + `cwd=业务工作区`，
   DSH 直接报错退出：

   ```
   dsh: session "session-****" was recorded in
   "…/default-workspace", not "…/业务工作区"
   ```

   之前 `dshrun` 把它当 `reason: empty` 吞掉（错误只在 stderr），面板上就是「没成功回复」，
   且**永远不会自愈**——旧 id 一直挂着。会话也因此没落进 业务工作区，侧边栏看不见。

2. **插件自管模型配置**：`dshconf.llm()` 用正则去刮 `cordis.patch.yml`、
   再去 `~/.dsh/.credentials.yaml` 抠 key、往 dsh 子进程注入 `ANTHROPIC_AUTH_TOKEN`。
   同一套模型配置在机器上有第二份解析，profile 一改就漂。

### 改法

- `dshrun.py`：`_invoke()` 单轮调用；`run()` 里遇到 `was recorded in` 就丢掉旧
  `--session-id` 在绑定工作区重开一个，新 id 自动写回 `chats.dsh_session`
  （轮询 `_draft_and_send` 与面板 `/api/draft` 两个入口都存）。
  不再注入任何 key（`_clean_env` 只清代理与 NODE_OPTIONS shim）。
- `draft.py`：dsh 引擎就绪判断改为「dsh 运行时在 + profile 在」，
  不再看 `api_key`；`llm.*` 收窄为 api 兜底的显式覆盖，不再刮 DSH 配置。
- `poller.llm_status()` / `config.public()`：不再回解析出的 model/base_url，
  标签改「跟随 DSH 配置」。
- **一次性 DSH 侧配置**：headless bundle 默认 `- id: credentials / disabled: true`
  （假设走启动时环境变量）。在 `~/.dsh/profiles/headless/cordis.patch.yml` 补
  `- id: credentials / disabled: false`，让 DSH 自己从 `~/.dsh/.credentials.yaml`
  解析 key；模型目录同时补 `glm-5.3-flash[1m]` 并设为默认（与 desktop profile 一致）。
  这是写到 `~/.dsh/` 的一次性配置，不是插件代码的一部分。

### 验证

- 复现：修前 `draft.draft(…, workspace=业务工作区, session_id=旧id)` →
  `ok: false, reason: empty`，detail 是那句 was recorded in。
- 修后同一调用 → `ok: true`，`session-****` 落在
  `~/.dsh/sessions/<业务工作区slug>/`（= 业务工作区 工作区），
  草稿正文正常产出。
- `python3 -m unittest discover -s tests` 67 项全过；`tests/run_tests.py` 98 项全过；
  `scripts/gate.sh --quick` 五项全绿。

## 15:40-16:00 真机验证 + 补齐「工作区可见」（0.7.1 追加）

用户要求用「示例对象 E」的会话真机验证修复。验证中发现**残留缺口**：
会话文件落对了目录，但 DSH 侧边栏的工作区里看不见。

### 根因（DSH 侧行为，非插件代码）

`workspaceRegistry.bootstrap()` 只在**首次初始化**（`state.initialized` 为假）
时把 sessions 目录按 cwd 收编进工作区；之后新建的会话永远不会自动登记进
`workspace.sessionIds`，侧边栏就不显示。插件用 `dsh --session-id` 新建的
会话全部命中这个盲区。

### 改法

- `lib/index.js`（宿主半，跑在 DSH 进程内）：`ctx.inject(["workspaceRegistry"])`
  拿到 DSH 自己的工作区服务；子进程事件 `attach_session` →
  `registry.resolveByPath(cwd)` → `entity.attachSession(sessionId)`。
  attachSession 会校验会话 cwd 必须等于工作区路径，错位会话被 DSH 拒绝。
  registry 未就绪时事件入队（上限 500），就绪后 flush。
- `server.py`：`_announce_attach()`（draft 成功后申报）；`_announce_all()`
  （启动时把已绑定的 (工作区, 会话) 全部申报一遍，修存量漏挂）。
- `poller.py`：自动回复路径同样申报。
- 原则不变：插件不写 DSH 的存储，只申报，由 DSH 自己校验落库。

## 17:00 spec 0004 实施：插件收缩为分身壳（未发版，v0.8.0）

用户拍板：插件只当壳（消息展示 + 通知 + 手动发送），脑子交回 agent 会话；

先做技术探针再动手，四个结论（只读，不改 DSH 本体）：

1. headless agent 有完整 shell 工具面：能跑 `echo`、读工作区文件、`command -v lark-cli` 有结果。
2. turn 中途 SIGTERM 后同 session 续跑正常：锁释放、turn 计数连续、历史连贯，
   agent 自己知道「上一轮 sleep 没拿到结果就被中断」。
3. 并发写同一 session：DSH 快速失败 `already owned by an active write handle`（exit 1），
   不排队、不损坏——插件状态机之外的第二道保险。
4. 插件 API 无 SSE/WS 推送原语 → 通知维持轮询；用户定 **60 秒**（拉取下限仍是 10 分钟，不动）。

- 新 `service/turns.py`：每实例 idle/running；burst 合并；running 时 SIGTERM→宽限→KILL
  →同 session 重起；DSH 锁错误按 running 处理；失败下一轮再喊。
- `service/dshrun.py`：`subprocess.run` → Popen + `Turn`（读线程解析 NDJSON、进程组终止）。
- `service/poller.py`：删起草管道（`maybe_service_reply` / `_draft_and_send` / ack / plan），
  改为命中即 `turns.wake`；本人新发言 → 更早待回标 `replied`（待回闭环）。
- `service/draft.py` 删除；`/api/draft` `/api/suggestion` `/api/chat/plan-confirm` 删除；
  新增 `POST /api/chat/session/reset`（新建会话）。
- `chats` 加 `session_bound_at` / `session_turns`；`mode` / `auto_send` / `reply_*` 保留列不读写。
- `config`：退役 `llm.*` / `reply.*` / `reply_guard` / `dsh.pre_draft`，`dsh.timeout` 默认 600。
- 面板：删起草/模式/自动发/模型设置；加实例状态、绑定会话、新建会话；tick 6s → 60s。
- 0003 spec 标记「已放弃（被 0004 取代）」。

## 19:10 工作区接线修正（spec 0011）

现场：示例对象 B 18:47:28 第一轮 turn 落在 `default-workspace`
（`session-****`），14 秒后改成 业务工作区 才起 `session-****`；
两条 turn 都被打断，且都没有进 `workspace.json`（attach 没发）。DB 最终
`dsh_session=""`。

根因（五处接线缺口）：

1. `chats.workspace=""` 时 `dshrun._pick_cwd` 静默选 DSH 默认，面板却显示「未绑定」；
2. 收件箱详情/群卡片/找群结果的「加入值守」都不传 `workspace`；人名搜索卡的
   默认值是 DSH 默认，不是用户上次选的工作区；
3. `/api/chat/workspace` 只改列：在飞 turn 不打断、旧工作区会话不解绑；
4. `wake` 打断旧 turn 时落库但不发 `attach_session`，新 turn 因 id 未变也不发；
5. 契约 01 写 `path`、实现读 `workspace`；空工作区时 `session_in_workspace`
   直接放行，旧 session 带着错 cwd 去续聊。

改法：

- `workspaces.resolve_for_chat` 返回 `source` / `fallback`；显式目录失效不静默回退。
- `dshrun._pick_cwd` 对显式不存在的路径直接报 `workspace_missing`；
  `_cwd_key` 用 realpath（macOS `/tmp`→`/private/tmp`）；空工作区不续旧 session。
- `turns._spawn` 用有效路径启动；`_remember_session` 在打断与续聊（id 未变）时都发
  `attach_session`；`interrupt()` 也申报在飞 turn。
- `server._apply_workspace`：有效 cwd 变化时打断在飞 turn、会话不在新工作区则解绑；
  `/api/chat/workspace` 同时接受 `workspace` / `path`，不给键=坏请求；
  `/api/watch`、`/api/chat/wake`、`/api/chat/session/reset` 可选带 `workspace`；
  `/api/chats` 增加 `workspace_effective*` / `workspace_fallback` / `workspace_missing`。
- 面板：`S.addWs` 记忆 → 最近在用 → DSH 默认；`joinWatch()` 统一带工作区；
  详情工作区行常显；现在处理/新建会话带当前选择；空工作区显示「跟随 DSH 默认」。
- 契约 01/02 与插件 README 同步。
