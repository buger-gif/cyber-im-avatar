## 画像两层拆分设计（spec 0031 / ADR 0008）

- 用户提出：现在群聊、私聊各有一份画像；群里的个人评价应该融到「某个人自己的文件」，
  群文件只放群内特殊要求与工作要求。要求先出方案，不直接动代码。
- 现状读数（`~/.im-standin`，只读统计，未打开画像正文）：`state.json` 165 个会话、
  9 个 `target`（7 私聊 / 2 群）、`profiles/` 11 份 Markdown（含 2 份 `.history.md`，
  合计约 41KB）。画像都还是旧四段模板；有一份私聊画像的 key 是 `ou_…`（飞书按
  `--user-id` 登记），说明「chat_id 就是人物 ID」的情况真实存在。
- 发现的问题：群里学到的成员评价只落在群画像；同一人换群/私聊读不到。会话工作本
  （群规、回复口径、成员角色）与个人评价混在一份文件里，起草时抓不到重点，整理时
  也难判断哪条能删。
- 设计（`docs/specs/active/0031-人物档案与会话工作本.md`）：
  - 人物档案 `profiles/people/<platform>/<person_id>.md`，键取消息发送者 ID
    （飞书 open_id / 企微 userid / 钉钉消息 senderId），显示名不做键；
  - 会话工作本沿用 `profiles/<platform>/<chat_id>.md`，只放本会话成立的要求与上下文，
    个人评价只留指针；
  - 归属判据「换一个会话遇到这个人还成立吗」；归因只认 ID 可确认的发言人；
    隐私上不把 A 会话上下文带进 B 会话；
  - 插件只给路径：首轮/开场给工作本 + 本批发言人档案（≤5），后续轮补新发言人，
    心跳给工作本 + ≤3 份档案；不加 `state.json` 字段、不升 version；
  - 新 API：`/api/persons`、`/api/persons/profile`（带 `base_mtime` CAS）、
    `/api/persons` DELETE；`/api/targets` 保留 `profile*`＝工作本并加 `person`；
    `forget` 不再删人物档案；
  - 旧画像懒迁移：agent 处理到某会话时先归档 `.history.md` 再拆分，确认不了 ID 的
    条目进工作本 `## 待归人物`，不写自动拆分脚本。
- 三路只读审计（子 agent）给了改动清单与坑：`turns.js` 载荷只带 `sender_name`、
  丢了 `sender_id`（必须补人物 ID 才能落对文件）；`/api/targets/profile` 以
  `platform+name` 寻址，重名/改名会串；`GET /api/targets` 的 `ensure` 有写盘副作用，
  人物列表不能照抄；Python 认 `env.json profile_file` 而 Node 不认，人物层改纯推导；
  活文档预算贴顶（`SKILL.md` 341/342、`01-api` 78/85、`02-storage` 101/105）。
- 落地文件：spec + plan、ADR `0008`（proposed）、`docs/decisions/README.md` 索引、
  `docs/specs/README.md` 下一个号 0032、`PROGRESS.md` 断点。**未改任何代码**，
  未动真实 `~/.im-standin`，未外发。
- 门禁：`python3 scripts/verify_docs.py` 0 违规；`bash scripts/gate.sh --quick` 五项全绿。
- 待用户拍板：①人物档案按平台 ID 建、显示名只做展示；②群工作本只留工作要求与成员指针；

  回前台立刻补；内容不变不重建 DOM、滚动位置保持；失败保留上次内容 + 顶部错误条。
- 改后读数（同一套脚本）：接口延迟 800ms 时正文出现 825ms → **7ms**；无缓存首开显示

  内容保留、错误条出现，重试后消失；长日报滚到 300px 后等 3 轮静默刷新 `pre` 仍是同一
  节点、`scrollTop` 仍 300；切到无文件日期显示「这一天没有日报」，回今天 0ms 出内容。
- 测试：`cd dsh-plugin && node --test` 181/181；`python3 tests/run_tests.py` 182 通过 /

## 人物档案指针每轮重复（14:30 修）

- 用户贴出私聊唤醒：每条新消息都重复同一段 `人物档案：- 若存… → …md`。
- 根因：`peopleFor()` 每轮都按「本批发件人」重新列，没记住这条会话已经给过谁；
  设计原意是「后续只补新发言人」，实现成了「每批都补本批全部」。
- 改法：`Turns` 增内存 `seenPeople`（key = platform:chat_id:session_id），首轮给全量并记账，
  后续轮用 seen 过滤；换会话/重开自然换 key。心跳列出的档案也记账，避免下一次真实消息再重复。
  失败/进程重启后最多重复一次，不影响正确性，不改 state。
- 测试：turns 56 通过；新增「后续轮只补没给过的人」「同一人再发不重复」两条。
