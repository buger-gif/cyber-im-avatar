## 值守分诊 spec（0040 / ADR 0012）

- 用户原话：「插件设计能不能跟 ai native 一点，当被拉进新群，或者某些人拉你进群 @ 你之后，
  你可以想办法自评价是否触发一个监听值班。你设计下给我个 spec」。
- 读代码确认的现状：
  - `refreshChatlist()` 每 `poll.interval_min`（默认 10 分钟）刷会话列表，`ensureChat()` 把
    新群写成 `watching=false`、`timer=-1`；`candidates()` 只选 `timer=1` 的群，所以新群
    不会被拉、也不会有 turn。
  - 插件是纯拉取，没有平台推送；没在盯的群里的 @ 看不见。`lark-cli event consume` 是另一套
    长进程形态，不在插件里。
  - 值守台判断需要的材料（群名、最近 10 条、@ 的人、人物档案、用户过去的值守偏好）在
    发现/探针后可得；当前没有任何一处让 agent 用它们做决定。
- 设计取舍：
  - 插件只做发现、基线、一次性探针（10 条、消费水位、不下载媒体、不唤醒）、排队、配额、
    决策文件校验与执行；判断交给 agent（铁律 8）。
  - 判断放在**全局值守台** desk session，不放在每个候选群自己的会话里；避免 ignore 的群
    也留下 DSH 会话，也让跨群判断口径一致。
  - 值守台固定 cwd `<state.dir>/duty/`，决策文件 `decisions/<event_id>.json`；agent 用普通
    `workspace-write` 就能写，不需要 `dsh.full_access`。
  - 决策只有 `watch` / `trial` / `ignore`；trial 到期复核一次，不能无限续期；分诊轮不向
    群里发消息，决定值守后才起接手轮。
  - 首次刷会话列表只建 `desk.baseline_at`，不排队；避免首次安装把最近 20 个群一次分诊。
  - 自动分诊有 `duty.max_per_day` 配额和 `duty.max_groups` 值守群上限；手动不受限。

## 补充：会话膨胀与私有工作区

- 用户追问：判断简单重复、会话可能很多，要不要给判断/监听单独一个工作区，不要和常规工作
  放一起。
- 结论：值守台固定 `<state.dir>/duty/` 私有 cwd，不注册用户工作区列表、不读项目、不写用户
  仓库；分诊只用一个全局会话，不按群建；按闲置 `2 × dsh.warm_min` 或
  `duty.session_max_turns`（默认 20）轮换，旧会话留在 DSH 历史（插件没有删除接口）；
  `ignore`/`failed` 记录按 `duty.record_keep_days`（默认 30）清理，未应用决策文件 7 天清理；
  `policy.md` 不清理。群工作仍留在原 workspace，沿用现有 `2 × warm_min` 寿命；
  `duty.max_groups` 限制同时值守群数。
- spec §4/§8/§9/§10/§11、plan、ADR 0012 同步；仍无代码/契约改动。

- 用户拍板选 (a)：只隔离「判断」；值守群会话仍用原 workspace，不强制搬进独立工作区。
  理由：群工作要读项目上下文、写群工作本；某个群要隔离就用现有 per-chat workspace。
  spec §4 与 ADR 0012 已记录。

## 补充：新群只 mention + 成本模型

- 用户拍板：新监听群一律 at 模式，不允许分诊开全量。决策文件去掉 `mode`；`watch`/`trial`
  恒写 `wake_mode=mention`；`mentionable=false` 的平台只能 `ignore`；用户手动把某个群改成
  「全部消息」仍走现有三态，不由分诊产生。
- 成本：事件驱动，不是定时心跳。0 个新群 → 0 次模型调用；每个新群 = 1 次 CLI 探针 +
  1 个分诊 turn；决定 watch/trial = 1 个接手轮；每个 trial 到期 = 1 个复核 turn；
  群轮询只花 CLI，不花 token，只有消息命中才唤醒群会话。
- 估算：分诊 prompt 1.5–3k 输入 / 0.2–0.5k 输出；值守台首轮 +8–15k（skill 注入，每会话一次）；
  接手轮 8–15k 输入；20 群日最坏约 0.4–0.9M 输入（取决于消息长度与会话历史）。
  旋钮：`duty.enabled` / `max_per_day` / `max_groups` / `trial_hours` / `session_max_turns`。
- spec §12 新增成本模型；plan/ADR/PROGRESS 同步。

- 修正：值守台改为**紧凑 prompt，不加载完整 `cyber-im-avatar` skill**；首轮固定约 1–2k，
  不是 8–15k。群接手轮才加载 skill（8–15k）。分诊 prompt 本身仍是 1.5–3k（10 条消息 +
  事实）；读 policy/人物档案另加 0.5–2k/份。

## 补充：定期 @ 清查（sweep）

- 用户要求：隔一段时间清查 @ 我的消息；某些 @ 如果不在值班群里，可能需要触发新值班。
- 方案：每 `duty.sweep_min`（默认 60）扫最近发现列表 top `duty.sweep_chats`（默认 10）个
  未值守群，每群拉 10 条，只看 `duty.sweep_lookback_hours`（默认 24）内的个人 @；sweep 本身
  0 token，命中 @ 才生成 `trigger=sweep` 的分诊事件。`ignore`/`failed` 可被新 @ 重开；
  `watch`/`trial`/`queued`/`triaging` 跳过；`@all` 不算。`duty.sweep_epoch` 去重，sweep
  不写 `last_sync`/`recent`/正常水位；`desk.last_sweep_at` 记录上次清查。`sweep_min=0` 关，
  企微/`refresh_chatlist=false` 不扫；top N + 24h 是兜底，不是全量审计。

  只把群 ID 存 `desk.baseline_group_ids`，不建 3k 个 chat；日常刷新命中这些 ID 的旧群直接
  跳过，不在集合里的才排队。升级清 `queued/triaging` + `trigger=added`，保留 sweep/manual。
- 值守判断改为一次性：每次 `resolveDesk` 新建会话，不复用 `desk.dsh_session`；prompt 去掉
  最近判断/人物档案/重复行；`session_max_turns` 保留兼容但不再生效；面板去掉该输入。
