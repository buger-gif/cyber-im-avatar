# 0020 进度卡按发信撤回，等待期跨指令

> 状态: implemented
> 日期: 2026-11-24
> 关联: spec 0061

## 背景

spec 0052 把进度卡绑在 DSH turn 上：turn 成功就 patch「处理完成」，之后 agent 在本地做画像 /
记忆归并，计数继续涨、卡片继续动。卡片发给目标 IM，目标的判断标准是「有没有给我发消息」，
不是 DSH 会话是否完成。0052 还明确不读工具参数，只发飞书私聊。

运行版 DSH 的 `session/event` 已经在 `tool/call.data` 里给出 `turn`、`callId`、`name`、
`arguments`（模型原始 JSON），有机会在不加轮询的情况下看到 `lark-cli` 发信调用。

## 决策

选了「等待期 + 发信即撤回」：卡片按一次连续等待期管理，不按 DSH turn；看到本会话的发信就
撤回卡片并结束等待期，没看到才按最终 turn 结束兜底；飞书群聊另设默认关闭的开关。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 继续按 turn/end 收口 | 发信后的本地归并会继续计数，目标看到「已完成」后卡片还在动 |
| 每 20 秒拉一次确认已发 | 增加拉取频率；发信调用本来就在 `session/event` 里，拉取只是绕路 |
| 只靠 agent 写 `[进度]` 完成标记 | 依赖模型自觉，漏写就回到旧问题；插件只能做确定性信号 |
| 发信后 patch「已回复」保留卡 | 目标已经收到消息，旧卡是噪音；用户明确要求直接撤回 |
| 每轮 turn 一张卡 | 连续指令会闪「已暂停 → 处理中」，2 分钟不断重置，可能永远不出卡 |
| 群聊共用私聊开关 | 群卡片全群可见，风险不同，需要单独默认关闭 + 单群覆盖 |

## 后果

- 接受：读 shell 工具的 `command`（0052 非目标的唯一例外）；只内存匹配，不落 state / 日志 /
  卡片。命令套脚本、raw API、变量拼接识别不了，靠 `chat.recent` 二次确认或最终 turn 兜底。
- 接受：`tool/call` 在执行前发出，发送失败也会收口；要零误报需等 `tool/result`，多 1–2 秒。
- 接受：撤回是高风险写操作，插件只对自己记录的 `progress.msg_id` 执行；撤回失败降级成
  「已回复」卡。
- 接受：群聊卡片全群可见；默认关，设置页全局 + 单群三态。
- 重新考虑的触发条件：`lark-cli` 命令形状变化导致识别率下降；或群卡片被反馈噪音过大。
