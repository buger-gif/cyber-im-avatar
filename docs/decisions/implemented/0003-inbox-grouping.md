# 0003 收件箱按会话聚合，不逐条堆叠

> 状态: implemented
> 日期: 2026-11-01
> 关联: `docs/architecture/02-data.md §收件箱聚合`、`docs/specs/contracts/01-api.md`

## 背景

收件箱原来一条消息一行。真实使用里同一个人会连发五六条（先问在吗、再发截图、再补一句），
一次刷新就吃掉大半屏，其余会话被顶到看不见的地方。用户原话：
「收件箱聚合下 按私聊人和群聊聚合 不要一直堆叠」。

## 决策

`/api/inbox` 默认按 `(platform, chat_id)` 归组：一个人或一个群只占一行，
行右侧是「时间 + N 条 + 展开箭头」，点箭头**就地展开**该会话其余几条（默认 3 条预览），
点行本身仍进会话详情。逐条模式保留为 `/api/inbox?group=msg`，排障用。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 按时间窗合并（同 5 分钟内的算一组） | 阈值是猜的；跨窗口的连续追问仍会分家，而不同会话的无关消息会被并到一起 |
| 折叠但只在服务端返回「最新一条」 | 展开时要再发一轮请求，交互变慢；预览 3 条一次带回更划算 |
| 前端做聚合（后端仍返逐条） | 计数与排序要在前端重算，`/api/status` 的角标与列表会对不上 |
| 虚拟滚动 / 分页解决长度问题 | 解决的是渲染性能，不是「同一会话重复占位」这个信息结构问题 |

## 后果

- **接受**：SQL 变成 `GROUP BY` + 二次查预览，两次查询而不是一次；量级（几千条）下可忽略。
- **接受**：排序键必须是**会话最后一条消息时间**，不是最后一条未读时间，否则老会话会因一条新消息反复跳顶。
- **接受**：`group=msg` 这条退路要一直留着——逐条视图是排查「为什么这条进了收件箱」的唯一入口。
- **重新考虑的触发条件**：单个会话待回条数经常超过 50（预览 3 条的形态会失效），
  或需要「按消息类型混排」的收件箱。
