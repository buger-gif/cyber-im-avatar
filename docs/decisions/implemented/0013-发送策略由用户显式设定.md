# 0013 发送策略由用户显式设定：值班单点 + 新建默认

> 状态: implemented
> 日期: 2026-11-12
> 关联: spec 0043

## 背景

0004 把「要不要发、发什么」整体还给 agent 后，插件侧不再有 `auto_send` 开关
（`docs/specs/archive/0004-skill-shell.md §退役清单`）。当时的发送策略靠用户在值守会话里
口头约定，README 写成「默认草稿审批，你明确说全自动后 agent 记住」。

实际运行暴露了三个事实：

1. 会话寿命是可变的：闲置重开、手动重开、换工作区都会换 DSH 会话，旧会话里的口头约定
   不会跟过去。agent 在新会话里重新问一次，用户于是「每次都被问」。
2. 同一时间不同值守会话可能处在不同策略：一个记住全自动，一个默认草稿。用户从面板看不出
   当前策略，agent 的行为也无法预期。
3. agent 在高风险内容上仍会停下（钱、合同、承诺、外部群），这部分是 skill 铁律，不能交给
   用户临时口头授权；但低风险的日常回复不应该逐条确认。

用户进一步明确：发送方式是**值班单点配置**，不是全局一刀切；全局只提供「新建值守时的
默认值」，而且用户自己的默认是全自动。默认只在新建时生效，之后改默认不覆盖已有值班。

## 决策

- `chats[].send_mode` 是每通值班自己的发送方式（`draft` / `auto`），新建时先留
  `""`，首次加入值守固化为当时的 `config.send_mode_default`；显式值不随默认变化。
- `config.send_mode_default` 是唯一全局项，只决定之后新加入值守的默认；仓库代码默认
  `draft`，用户可在设置里改成 `auto`。
- 插件只在每一轮可能产生回复的唤醒/开场载荷里声明**该值班实际生效值**，agent 按它执行；
  不解析、不代发、不存正文，不恢复起草或审批队列。内容判断仍归 agent，风险铁律优先于模式。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 只做全局开关 | 不同客户/群需要不同节奏；一个会话的选择会被带到所有会话，用户已明确否决。 |
| 动态「跟随全局默认」 | 用户要求「默认是新建的时候的默认状态」；改默认不应回头覆盖已有值班。要改就点那一下。 |
| 每个值班各自设，不给全局默认 | 每加一个值班都要多点一次；新建默认解决重复操作。 |
| 插件做草稿箱 + 面板点发送 | 要把 agent 的输出和待发正文落进插件状态；解析、审批、正文存储全回到插件，正是 0004 删掉的两套脑子。 |
| 把模式做成 agent 自己维护的文件 | 插件读不了 agent 的自然语言；再加一份文件等于第三个事实源，且换会话/换工作区仍可能漂。 |
| 全自动也由插件做关键词风险闸门 | 插件不读正文；关键词会误伤正常回复，还会和 skill 铁律各长一套。风险判断留给 agent。 |
| 仓库默认全自动 | 以本人身份外发是高风险动作；代码默认保守，个人把新建默认设成 `auto` 即可。 |
| 复用退役的 `reply` 段 | `reply.*` 是 0003 起草管道的遗产，赛博语义容易被误读；`send_mode` 更窄、更清楚。 |

## 后果

- 接受：全局粒度只剩「新建默认」，要改已有值班必须逐条切；这是用户要的单点语义。
- 接受：模式只是载荷里的一行声明，插件无法在技术上阻止 agent 违规发送；兜底仍是 skill
  铁律、默认草稿、切全自动时的二次确认。
- 接受：全自动模式下 agent 直接调用平台 CLI 发送；插件不记录发送正文，面板只从平台拉回
  「我」的消息，和今天的手动发送一致。
- 接受：切换模式对正在跑的那一轮不生效，下一轮载荷才带新值；面板文案要说明。
- 接受：存量已值守会话在升级时被补成显式值（按旧全局值/默认值）；未值守会话留
  `""`，等首次加入值守再取默认。
- 重新考虑的触发条件：
  - 用户明确需要「多个值班批量切发送方式」；再加批量操作，但不改单点事实源；
  - agent 在 `auto` 下出现可复现的越界发送，且 skill 铁律无法收敛；
  - 平台提供可编程的发送审批通道，能在不存正文的前提下做确定性闸门。
