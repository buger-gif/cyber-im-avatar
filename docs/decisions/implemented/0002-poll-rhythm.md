# 0002 拉取节奏：分钟级下限 10 分钟，群默认不拉

> 状态: implemented
> 日期: 2026-10-31
> 关联: `docs/specs/contracts/03-config.md`、`docs/architecture/02-data.md`

## 背景

早期版本每轮拉**所有**会话，间隔按秒配。真实账号的会话数是几百到两千级别，
每次拉取都是一次 IM CLI 调用：几十个会话跑一轮就要几十秒，CPU 和接口配额一起烧，
而绝大多数轮次什么都没变。

同时群聊的成本结构完全不同：一个 500 人群每 10 分钟拉一次，等于用本人账号在群里做全量监听，
消息量大、噪音多，还涉及「以本人身份持续在线」的合规问题。

## 决策

1. 定时轮**只拉该拉的**：私聊按 `dm_scope`（recent / all / watched），群**默认一个都不拉**，
   只有显式勾了「定时检测 @我」（`timer=1`）的群才进轮询。
2. 间隔按分钟算，**硬下限 10 分钟**，填更小一律夹到 10。
3. 点开会话、手动「拉一轮」不受间隔限制，但受 20 秒冷却约束，防连点打穿接口。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 保持秒级、只加并发 | 并发不减少调用总量，只是更快地把配额打完 |
| 用 IM 的推送 / webhook | 三个平台都没有给「以本人身份收全部会话」的推送通道；有的只是机器人事件 |
| 群也默认拉，靠过滤降噪 | 成本在拉取侧不在展示侧；拉回来就已经花了调用与磁盘 |
| 手动模式（完全不自动） | 真有人找的时候会漏；用户要的是「别乱拉」，不是「别拉」 |

## 后果

- **接受**：群消息默认看不到，必须点进去才拉一次。要做群客服得逐群勾「定时检测 @我」。
- **接受**：10 分钟意味着最坏 10 分钟延迟。值守场景够用（人不会在 10 分钟内换话题），
  赶时间可以手动拉。
- **接受**：配置项变多（`dm_scope` / `dm_recent` / `cooldown_sec`），面板必须解释清楚
  「定时拉哪些」与「收件箱显示哪些」不是一回事。
- **重新考虑的触发条件**：出现平台级推送能力，或用户量级让「按需拉」不能满足响应要求。
