# 0018 没点你名的群消息：给条数 + 按需在线拉

> 状态: implemented
> 日期: 2026-11-18
> 关联: spec 0051（`§6 C 型态`）

## 背景

发言权的默认口径允许「谁都没点、但问题是要你答的」这一类回复（0017）。可唤醒范围默认还是
「只 @ 我」：`process()` 把没点我名的群消息判成 `fyi` / `state=ignored`，正文不保留，
`wakeMessages()` 只收有正文的待回消息——**这类消息在开场轮之后根本到不了 agent**。
发言权说能回，消息却送不到，等于口径空转。

同时不能简单把群默认改成「全部消息」：每来一条消息就是一次模型轮次，本机 314 个会话、
32 个全自动群里随便几个活跃群就能把成本打穿，也违反拉取节奏的成本模型（ADR 0002）。

## 决策

唤醒范围不动。下一次唤醒时，插件把「上次交付之后、没点我名的消息」**只报条数**带进载荷：
`另有 N 条没点你名的群消息没转给正文；判断需要时按 skill 在线拉最近的群消息看。`
模型自己决定要不要拉，拉一次 CLI，正文不落插件状态。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 新群默认「全部消息」 | 每条消息一次模型轮次，成本随活跃度线性涨，且和「群默认不拉」的成本模型冲突 |
| 把这些消息的正文留在 `recent[]` 一起交付 | 状态里长期存群里的公开正文，隐私面变大；`recent[]` 上限 10 条也装不下；契约 02 要改 |
| 定时扫一轮「没唤醒但有新消息」的群 | 又多一条轮询节奏，等于把「全部消息」换个壳 |
| 什么都不做，靠面板显示「最近 N 条没唤醒」 | 用户能看到，但 agent 看不到，默认口径里「没点任何人也可能要回」这条永远落不了地 |
| 让 agent 每轮无脑拉一次群消息 | 每次唤醒多一次 CLI 调用和一份上下文，绝大多数轮次白花 |

## 后果

- 接受：**可能晚一轮**。没点你名的消息要等下一次被点名（或别的唤醒）才会被提示，不会立刻处理。
- 接受：条数是「至少这么多」——`recent[]` 上限 10 条，插件只数上次交付之后的，超出部分不精确。
  载荷里按条数说，不装作是全集。
- 接受：判断权在模型（要不要拉、拉了怎么回），插件只给计数和命令提示，不代拉、不代判。
- 重新考虑的触发条件：
  - 真实使用中「被点名时才补看」经常太晚（用户明确要求准实时）；
  - 平台提供的读消息接口变便宜（比如增量推送），可以改成事件驱动；
  - 出现「agent 从不拉」的样本，说明这行提示不够，需要考虑主动交付正文。
