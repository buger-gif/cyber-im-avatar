# 0004 服务对象画像用文件，消息只留指针

> 状态: implemented
> 日期: 2026-11-02
> 关联: spec 0012

## 背景

服务对象页原本展示 `env.json` 里 `targets.<platform>.<name>.profile` 的笔记数组：
一条一行、带日期。它是「历史观察流水」，不是一份能直接读、直接改的客户画像。
同时 `panel.db.messages` 保存了拉到的消息正文，包括已回、已忽略和只是知会的消息；
本地因此在无界积累聊天原文，而平台本身支持按 `chat_id` / `msg_id` 在线查询。

## 决策

- 每个服务对象一份 Markdown 画像，落在
  `~/.im-standin/profiles/<platform>/<chat_id>.md`；`env.json` 只留
  `profile_file` 索引，不再保存画像正文。
- 画像由 skill 维护：壳内 agent 在回复末尾提交完整画像
  `<!-- im-profile-update ... -->`，插件代写（沙箱写不了 `~/.im-standin`）；
  面板也可以直接编辑同一份文件。
- 本地 `messages` 只做指针 + 待办索引：`new` / `opened` 的私聊与 @我保留正文，
  `replied` / `ignored` / `fyi` / `out` 清空正文；历史正文打开会话时在线拉。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 继续把画像存成 `env.json.profile` 笔记数组 | 用户要的是一份画像，不是逐条回看历史；`env.json` 也会越写越像聊天记录 |
| 所有对象共用一份 `profiles.md` | agent 每次要读全部对象，违反 skill 的「最小上下文」 |
| 消息正文全部不落库 | 收件箱预览、待唤醒批次、待回计数都依赖待回复正文，每轮线上拉会让轮询成本翻倍 |
| 按时间删 `messages` 行 | 消息再次进入拉取窗口时会被当成新消息，重新变待回 |
| 给沙箱加 `~/.im-standin` 可写根 | DSH 不提供追加可写根；`danger-full-access` 是整机写权限，代价远大于收益 |

## 后果

- 画像文件成为新的个人数据落点：`--delete-data`、权限（700/600）、备份都要覆盖它。
- 打开会话依赖平台在线查询；企微只有近 7 天时间窗，离线时只能显示本地指针。
- agent 的画像更新多了一条「回复末尾块」协议；块缺失时画像保持不变，不会回滚。
- 若以后平台提供稳定的历史查询 API，可把 `fetch_thread` 扩展到更久，而不改存储。
