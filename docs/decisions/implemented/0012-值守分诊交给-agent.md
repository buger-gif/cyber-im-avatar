# 0012 值守分诊交给 agent：私有值守台判断，插件只搬事实

> 状态: implemented
> 日期: 2026-11-09
> 关联: spec 0040

## 背景

插件现在只在用户手动「加入值守」之后才拉群；新群出现在会话列表里（飞书 / 钉钉；企微当前
没有会话枚举）只会被 `ensureChat()` 登记成 `watching=false`、`timer=-1`，没有 turn，也没有
面板入口。没在盯的群里有人 @ 你，插件同样看不见——它是纯拉取，没有平台事件。用户要的是：
被拉进新群、或新群里有人 @ 你之后，分身自己判断这个群值不值得盯，再决定要不要进入值守；
并且**隔一段时间清查一次 @ 我的消息**，未值守群里的新 @ 也要能触发新值班。

现有约束：

- `AGENTS.md §设计铁律` 第 2 条：群默认不拉；第 8 条：插件只做确定性搬运，判断归 agent。
- 一个宿主进程、零端口、运行时零第三方依赖；消息正文只在本机，不进日志。
- 没有拉群事件；`lark-cli event consume` 是另一套长进程形态，不在插件里。
- 新群判断需要语义：群名、最近消息、@ 你的人、这个人的档案、用户过去的值守偏好。
  这些不是 `watching` 一个布尔值能表达的。

## 决策

插件负责发现、一次性探针、排队、校验与执行；安装/启动时初始化 `policy.md` 的四段初始版本。判断交给一个**全局值守台** agent 会话：

- 新群（基线之后）入队；探针只拉 10 条、消费水位、不下载媒体、不唤醒。
- **判断只发生在两类事件**：新建/首次发现时判一次；之后每次 sweep 发现**新的个人 @**
  时再判一次（同一条 @ 只一次）。没有 @ 不跑模型；已在值班的群 @ 直接进群会话，
  不再判「要不要值班」。默认 `trial_hours=0`，严格两段式；显式打开试用（`>0`）才多一次
  到期复核。
- **定期 @ 清查**：每 `duty.sweep_min`（默认 10 分钟）只处理**基线之后、未值守的新群**
  （不做 top N）。**Feishu 直接拉 `im +messages-search --is-at-me --chat-type group`**，
  一条搜索覆盖所有 @我，不再逐群拉；结果里的 @all / @everyone 必须用 `isMention` 过滤。
  DingTalk 没有 @我 搜索，退回逐新群 `+chat-messages`；WeCom 没有 mentions，不扫。
  只认新的个人 @（24h 内、`sweep_epoch` 去重），命中生成 `trigger=sweep` 新事件；
  `ignore` / `failed` 也能被新 @ 重开，`watch` / `trial` 跳过；**存量群完全不扫**。
  sweep 本身 0 token，不下载媒体、不写日志、不动正常水位；`sweep_min=0` 可关。
- **群成员硬门**：`duty.max_group_members` 默认 10；Feishu `+chat-members-list` 只数
  `users[]`，>10 或未知（DingTalk/WeCom/truncations）时自动路径只能 `ignore`，插件拒绝
  watch/trial；手动可以强制开。已经在值班的群后来长到 >10 不自动停。
- 值守台固定 cwd 为 `<state.dir>/duty/`，是**插件私有工作区**：不注册到 DSH 的用户工作区
  列表、不读项目文件、不写用户仓库；agent 用普通 `workspace-write` 写
  `decisions/<event_id>.json`，不需要 `dsh.full_access`。群工作仍留在原 workspace。
- 分诊只用一个全局值守台会话，不按群建；按闲置 `2 × warm_min` 或
  `duty.session_max_turns` 轮换，旧会话留在 DSH 历史（插件没有删除接口），`policy.md` 与
  最近 5 条判断保证换会话不丢口径。
- 值守台用**紧凑的插件 prompt**（约 1.5–2.5k 的职责/口径段），**不加载完整
  `cyber-im-avatar` skill**；它只做注意力判断，不需要 IM 闭环/平台命令/画像规则。
  群接手轮才加载 skill，照常干活。
- 决策只有 `watch` / `trial` / `ignore`；`trial` 需 `trial_hours>0`（默认关），到期由值守台
  复核一次，不能无限续期。
- **新监听群一律 `mention`**：决策文件没有 `mode`，`all` 不进入分诊；`mentionable=false`
  的平台只能 `ignore`。用户手动把某个群改成「全部消息」仍是现有三态能力，不由分诊产生。
- 分诊轮不向群里发消息；决定值守后另起接手轮，由群自己的会话按 `SKILL.md` 决定回不回。
- 用户手动操作优先；决策理由进 `state.json`，面板可见可推翻。`ignore` / `failed` 记录按
  `duty.record_keep_days` 清理，`watch` / `trial` 保留；未应用决策文件 7 天清理。
- **用户拍板（2026-11-09）**：只隔离「判断」——分诊/值守台在私有工作区；值守群会话仍用
  原 workspace，不强制搬进独立工作区。群工作要读项目上下文、写群工作本，搬走会丢上下文；
  某个群确实要隔离时用现有 per-chat workspace 绑定。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 插件里写规则（@ 就盯、大群不盯、关键词） | 判断需要群名语义与用户角色；规则会在 Node 与 prompt 里各长一套，互相打架。铁律 8 明确判断归 agent。 |
| 新群一律自动 `timer=1` 盯 N 小时 | 营销群、大群、临时群也进轮询；成本不可控，且没有「自评价」。 |
| 分诊也允许 `all` | 用户明确要求新监听群一律 at 模式；全量群噪声与模型成本高，自动判断不该替用户开全量。要全量由用户手动改三态。 |
| 只在发现新群时看，不做 @ 清查 | 已存在的未值守群有人 @ 你，插件永远看不见；用户要求定期兜底。 |
| Feishu 也逐群扫，不用 `--is-at-me` | Feishu CLI 已提供跨群 @我 搜索，一条调用就够；逐群扫是纯浪费。 |
| 每次清查连存量群一起扫 | 用户明确说已有群完全不用考虑；只扫基线之后的新群，存量群不读、不分诊。 |
| 清查也跑模型逐群判断 | 绝大多数群没有个人 @，跑模型纯浪费；sweep 只做 CLI 过滤，命中个人 @ 才起分诊。 |
| 依赖平台 mention feed / 推送 | Feishu 有 `--is-at-me` 搜索但不是事件推送；DingTalk/企微没有等价能力。按平台做直接搜索/逐群回退，不假装实时。 |
| 大群也自动 watch | 用户要求超过 10 人不自动开监听；大群噪声大、@ 多。`max_group_members=10` 是硬门。 |
| 成员数未知也放行 | 无法验证是否超过 10 人；宁可自动 ignore、面板提示手动，也不违反硬门。 |
| 清查发现 @ 也不重开已 `ignore` 的群 | 新的个人 @ 是新的信号；`ignore` 只对当时那条有效，`sweep_epoch` 保证同一条不重复。 |
| 每个新群都在面板问用户 | 用户不在时等于没有分诊；比现在的开关还重。 |
| 每个群用自己的 DSH 会话做分诊 | 被 ignore 的群也会留下会话，侧边栏被塞满；跨群判断也不一致。 |
| 把值守台注册成用户工作区 / 放进项目仓库 | 污染 DSH 工作区选择器，项目里多一个无关目录；判断不需要项目文件，独立私有 cwd 已经够。 |
| 值守台长期一个会话跑到底 | 判断简单重复，上下文越积越长，缓存与费用都吃亏；`policy.md` + 最近 5 条判断足够，按闲置 / 轮数换新。 |
| 把值守群也搬进值守台工作区 | 群工作要读项目上下文、写群工作本；搬走会丢上下文。值守台只判断，群工作留在原 workspace。 |
| 值守台也加载完整 `cyber-im-avatar` skill | 一次固定注入 8–15k token，而判断只需要事实 + 决策 schema；平台命令、画像规则、回复闭环都用不上。群接手轮才需要完整 skill。 |
| 插件删旧值守台 / 群会话 | DSH 没有删除会话接口；只能解绑、不再使用，旧会话留在历史，由用户自行清理。 |
| 全局值守台 + HTTP 路由 / agent tool 写决策 | 插件没有稳定本地端口；DSH tool 注册不是本仓库的稳定契约。文件是 agent 本来就会写、插件能校验、测试能覆盖的通道。 |
| 让 agent 在分诊轮直接回 @ | 判断与对外发言混在一起，一次误判就是全群可见的消息。拆成判断轮 + 接手轮。 |
| 默认强制 24h trial | 用户要求两段式：新建判一次、之后只在新的个人 @ 时再判；默认 trial 关，避免每个新群多一次定时复核。要试用可显式打开。 |
| 允许无限 trial 续期 | 等于永久轮询，只是把决定拖后。 |
| 决策直接写 `state.json` | agent 没有事务写，容易和插件抢写；插件是唯一 writer，文件是窄接口。 |

## 后果

- 接受：每个新群一次探针 + 一次值守台 turn；决定值守再加一次接手轮。用每日配额、
  值守群上限、一次 tick 一个来兜成本。
- 接受：Feishu 的 `--is-at-me` 搜索结果 + 候选新群的上下文会进这一次 DSH turn；
  DingTalk 逐新群读最近 10 条；存量群不读。不下载媒体、不写日志、不传第三方；总开关可关。
- 接受：DingTalk/WeCom 没有成员数，自动路径只能 ignore；Feishu 也只在能拿到 `users[]`
  时自动开。手动 `/api/watch` 仍是出口；这是为了不违反 >10 人的硬门。
- 接受：发现最坏晚 10 分钟；这是拉取模型的固有代价。
- 接受：值守台是一个真实 DSH 会话，用户可能在里面聊天；分诊遇到在飞 turn 只排队、不打断。
- 接受：旧值守台/群会话留在 DSH 历史，侧边栏会话数仍可能增长；插件没有删除接口，只能
  换绑、不再使用。靠“全局一个 + 轮换 + `max_groups`”把活跃会话压住。
- 接受：`ignore` / `failed` 记录到 `record_keep_days` 后清掉，旧判断理由不再显示；
  `watch` / `trial` 不清，用户仍可手动重判。
- 接受：分诊只做 `mention`，非 @ 的群消息不会唤醒群会话；要全量只能用户手动改三态，
  这是有意的成本/噪声边界。
- 接受：sweep 每 10 分钟扫**基线之后、未值守的新群**（不做 top N），Feishu 每 10 分钟 1 条搜索；
  只读每群 10 条、不下载媒体、不写日志；`sweep_min=0` 可关。只覆盖新群 + 24h，
  存量群永远不扫；更早/未发现的新群 @ 需要手动。
- 接受：已 `ignore` 的群被新的个人 @ 重开分诊，可能产生额外 turn；`sweep_epoch` 保证同
  一条 @ 只触发一次，用户可 block 该群或关 sweep。
- 接受：值守台的窄规则放在插件 prompt（`buildDeskPrompt`）而不是 `SKILL.md`；它只服务
  这一个判断，不随 IM 闭环规则漂移。群接手轮仍由 `SKILL.md` 驱动。
- 接受：换值守台会话会冷启动；首轮带 `policy.md` 与最近 5 条判断，口径不丢但要多读一点。
- 接受：agent 可能误判；默认 `mention`、trial 可选（默认关）、面板推翻、上限，分诊轮不发言，
  误判不会立刻变成对外消息。
- 重新考虑的触发条件：
  - 平台/CLI 提供稳定的拉群事件，或 DSH 提供稳定的 agent tool 注册接口；
  - 探针隐私或模型成本被用户明确反对；
  - 值守台会话成为瓶颈（长任务占用导致分诊长期排队）；
  - 误判率证明「默认 mention + trial 开时」仍不够保守。
