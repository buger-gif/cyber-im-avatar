# 0008 画像拆两层：人物档案按人一份，会话工作本按会话一份

> 状态: implemented
> 日期: 2026-11-05
> 关联: spec 0031

## 背景

现状一个会话一份画像 `profiles/<platform>/<chat_id>.md`（ADR 0004），四段都是
「对方是谁 / 沟通偏好 / 在意与忌讳 / 历史结论」。私聊里这套四段大致等于那个人；
群聊里同一套四段却同时容纳了两种东西：

- **人物评价**：某个成员是谁、怎么说话、忌讳什么；
- **会话要求**：这个群该不该回、要不要先 @、什么不能在群里说、谁负责什么。

后果是同一人的评价被会话切开：在群里学到的张三，私聊里读不到；换一个群遇到张三，
agent 仍然从零判断。同时群工作本被人物评价撑大，起草时抓不到本群真正的口径。

## 决策

把画像拆成两层，按内容归属而不是按会话归属：

- **人物档案**：`profiles/people/<platform>/<person_id>.md`，按平台消息发送者 ID
  一份，跨私聊/群聊复用；只写跨会话稳定的人物评价。
- **会话工作本**：`profiles/<platform>/<chat_id>.md`（路径不变），只写本会话成立的
  群规、工作要求、成员角色指针与会话结论；个人评价以指针引用人物档案，不复制。
- 插件只做确定性推导：给唤醒载荷人物 ID + 档案路径；读写、归因、迁移由 agent 按
  `SKILL.md` 完成。旧画像懒迁移（不写脚本自动拆），先归档 `.history.md` 再重写。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 在群画像里加「成员评价」小节 | 人的评价仍然散在多个群和私聊里，只是把混装挪了个位置 |
| 显示名做文件名/键 | 重名、改名、同名不同人会串；面板按名字寻址已经踩过这个坑 |
| 每人一份、会话不再单独存 | 群规与工作要求和人物评价是两种生命周期，混在一份里整理和读取都会变慢 |
| `~/.im-standin/people/` 顶层新目录 | 删除/权限/备份/隐私测试都要多覆盖一处；`profiles/` 子树已覆盖这些路径 |
| 插件维护 `state.people` 索引 | 双写漂移 + 要升 state 版本；面板扫目录 + `recent` 反查已经够 |
| 脚本自动拆旧画像 | 归属是语义判断；脚本拆会静默错归因，违反「不替你说错话」 |

## 后果

- 接受：一轮唤醒可能读 1 份工作本 + 最多 4 份人物档案（按发言人给路径，不扫目录）；
  人物档案跨会话累积更快，需要 8/12KB、20 条结论与心跳整理兜底。
- 接受：钉钉 `senderId` ≠ `userId` 的双 ID 问题不在本期自动解决，档案头记录双 ID +
  合并规则，留真机验收。
- 接受：旧画像不是一次性迁移，而是 agent 处理到某会话时逐步拆；`## 待归人物` 兜底
  期间同一事实可能短暂两处可见。
- 重新考虑的触发条件：如果实测发现 agent 在一轮里读档案的 token 成本显著高于
  按需拉取；或者人物档案普遍撞 12KB、整理收益不足以抵消成本，就回到「会话单层 +
  人物只做按需查询」的另一条路（ADR 0004 的服务对象画像保持不动）。
