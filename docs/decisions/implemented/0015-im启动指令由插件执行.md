# 0015 IM 启动指令由插件确定性执行，一条搜索覆盖未值守会话

> 状态: implemented
> 日期: 2026-11-12
> 关联: spec 0046

## 背景

spec 0029 / 0039 把「本人 @ 自己」做成 `kind=cmd` 并唤醒 agent。用户在 IM 里 @ 自己说一句
「启动」，想要的是**就地开启值班**，等价于面板「加入值守」，而不是让 agent 再解释一遍。

约束有三条：不能逐会话轮询未值守的群 / 私聊（成本模型）；同一 `platform:chat_id` 只能有
一个值班会话；未值守会话也必须能在飞书里被发现。已实测飞书 `+messages-search` 可用
`--sender <本人> --at-chatter-ids <本人>` 跨 p2p / group 搜到自 @ 消息（含 `chat_type` /
`mentions`），一条搜索即可代替逐会话拉取。

## 决策

- 「本人发送 + @ 本人 + 正文含关键词」由插件消费成确定性开关；关键词与开关在设置页可改，
  默认「启动」。
- 已值守会话在快车道即时识别；未值守的飞书会话由 `maybeCommandScan` 每 10 分钟发一条
  `+messages-search`（本人发送、@ 本人、最近 20 分钟），本地再按 `isMention` / 关键词复核。
- 同一 `platform:chat_id` 已有 `dsh_session` 或正在启动 → 只写 `already` 冲突，不新建；
  `watching` 但会话为空只补开，不新建第二个。
- 命中关键词的那条消息由开关消费，不再作为普通 `cmd` 交给 agent；开场 turn 的上下文里
  仍能看到它，但载荷明确「它只是开关，不要回复」。
- 企微 / 钉钉没有跨会话搜索能力：只在已值守会话里即时识别，不假装「任意位置」。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 让 agent 收到 `cmd` 后自己调 API 启动 | 要先花一轮模型调用，且插件 API 没有给 agent 的稳定入口；开关应由插件确定性执行 |
| 只支持已值守会话 | 用户明确要「不论何时何地」；飞书已有跨会话搜索，不利用就只能让用户先回面板 |
| 逐会话轮询未值守的群 / 私聊 | 把 IM 接口当靶子打，违反快慢车道成本模型；一条窄搜索就够了 |
| 为飞书自 @ 建事件订阅 | 用户身份收不到完整的 user↔user 私聊事件；现有 CLI 也没有稳定 feed |
| 已有值班时再开一个新会话 | 同一 chat 键与 `dsh_session` 单值本来就只能绑一个；两个 turn 会抢同一会话 |
| 自动回一条「已启动」 | 自动对外发言不在本次授权内，群里还会制造噪音；面板状态足够 |
| 把关键词消息也交给 agent | agent 会对开关本身回话，尤其在群里；用户要的是开关，不是对话 |
| 用严格前缀 / 独立命令语法 | 自 @ 已是显式动作；「@我自己 启动值班」这类自然写法不应被挡 |

## 后果

- 接受：飞书未值守会话最多约 10 分钟延迟；要即时只能先面板加入。用户可关闭扫描
  （`command.enabled=false`）或改关键词。
- 接受：企微 / 钉钉只在已值守会话里生效，这是平台搜索能力缺口，已写进 README 与
  `references/`。
- 接受：关键词选得太宽会把普通自 @ 消息消费成启动开关；设置页提示关键词应短而明确，
  改词立即生效，无需迁移。
- 接受：启动失败不回滚 `watching`，与面板加入一致；面板显示 `command.result=failed`。
- 接受：飞书搜索结果含正文但只在本机过滤，不写日志、不上传；`chats[].command` 只存结果
  与消息 ID，不存正文。
- 重新考虑的触发条件：
  - 飞书搜索接口不再支持 `--at-chatter-ids` / 自 @ 消息，或新增了更实时的事件源；
  - 用户需要「停止 / 重启」等第二条指令，届时抽独立命令表而不是继续堆关键词；
  - 出现跨聊天误启动的真实事故，需要改成严格前缀或二次确认。
