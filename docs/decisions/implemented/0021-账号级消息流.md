# 0021 账号级消息流替代逐会话轮询

> 状态: implemented
> 日期: 2026-11-27
> 关联: spec 0065、0066

## 背景

值守快车道原先每 60 秒对每个候选会话各拉一次「最新 N 条」，30 个会话就是每分钟 30 次请求，
且刷屏超过 10 条时窗口外的 @ 会被水位直接跳过（`last_epoch` 推进到最新，消息从未进过缓存）。
用户要求：不漏 @，同时**降低对飞书后端的请求量**，触发频率不能降。

实测发现 `lark-cli im +messages-search` 在不传 `--query`、只给 `--start/--end` 与
`--chat-id a,b,c` 时，会返回这些会话在窗口内的全部消息（p2p / group / topic / 卡片 / 本人消息），
带 `has_more`；单次 1.8–2.5 秒，索引里最新消息比上一轮逐会话拉取还新 60 秒。列表接口看不到
线程 / 话题消息（固定 `only_thread_root_messages=true`），这条流能看到。

## 决策

快车道改成**一条账号级消息流**：每 60 秒一次 `+messages-search`（按值守会话收窄 + 时间窗），
本地分类后按会话写进带 `delivered_at` 的待投集合；慢车道从「再拉一轮候选」改成「每 10 分钟
区间完整读对账」，补流可能漏掉的消息。请求量从 O(会话数) 降到 O(1)。

## 备选

| 备选 | 为什么不行 |
| --- | --- |
| 逐会话区间读（时间窗 + `complete`） | 正确，但请求量仍是 O(会话数)：30 次/分钟，安静分钟也固定花 30 次 |
| 先查「哪些会话有未读」再拉（feed / chat-list 探针） | 把触发绑到人的已读状态；多一次探针，只省安静会话的读 |
| 只上 @ 兜底搜索，不改读取 | @ 能到，但私聊来信与非 @ 上下文仍静默缺段，缺口无法记账 |
| 只改读取，不上兜底 | 页数上限、索引延迟、停机补读三个口子下 @ 没有保证 |
| 把命令扫描也并进这条流 | 流按 `--chat-id` 收窄到值守会话；并进来就要读未值守会话的正文，越界 |
| 事件订阅 / 长连接 | 看不到 user↔user 私聊，要 bot 进群，与「以本人身份轮询」相反 |
| 用会话未读数决定拉谁 | 把「要不要处理」绑到人有没有在手机上看过；用户扫一眼，分身就永远不处理 |
| 提高 `per_chat_limit` 或缩短轮询间隔 | 只挪阈值、负载还涨；不解决「窗口就是全部」的错误前提 |

## 后果

- 接受：依赖搜索索引。用慢车道每 10 分钟区间对账兜底，补投并记 `runtime.stream.missed`；
  索引漏一条最多延迟一个对账周期，不会永久丢。
- 接受：空 query 的「无过滤」语义依赖上游实现；首次失败当轮降级为逐会话区间读，面板红字。
- 接受：流结果没有 `reply_to`；要唤醒时对该会话补一次最近 10 条（每唤醒一次，不是每跳一次）。
- 接受：窗口被截断（只可能停机补读）时只保证 @：追加一次 `@我` 搜索，其余记
  `runtime.stream.truncated_at`，靠对账补齐。
- 接受：**触发必须有硬时间窗，历史不回溯**。实测重载后第一轮把 31 个会话的旧账全补了一遍，
  一次拉起 13 个 turn / 10 个新会话。现在只处理最近 10 分钟的消息；窗口外只留
  `skip="out-of-window"` 记录，不进批次、不建会话；`last_epoch` 之前的历史一律不看（旧 bug
  漏掉的 @ 也不补）。`seen`（50 个 ID）是持久触发记录，老 state 用 `recent` 播种；全局每分钟
  最多 5 个会话兜底。代价是「离线很久后最早的 @ 不会叫醒」，面板有记录与缺口，可手动处理。
- 平台差异：企微没有跨会话搜索、钉钉没有时间窗，各自保持逐会话区间读 / 采样，不假装统一。
- 重新考虑的触发条件：搜索接口收紧空 query / `--chat-id` 过滤；对账持续发现大量漏项
  （`stream.missed` 持续增长）；或「迟到 3 分钟不叫醒」导致真实 @ 被长期搁置（看面板待回）。
