# 决策记录（ADR）

> 记「拍过板、且当时有其它选项」的选择。没有备选方案的实现细节属于 spec，不属于这里。
> 目的只有一个：**别把已经否掉的方案再提一遍**，以及知道当初为什么忍了它的缺点。

## 目录即状态

| 目录 | 含义 |
| --- | --- |
| `docs/decisions/proposed/` | 已想清楚、还没实施，等时机或等验证 |
| `docs/decisions/implemented/` | 已落地并在用 |
| `docs/decisions/rejected/` | 认真考虑过、明确不做（**最有价值的一类**，防止反复重提） |

编号四位递增，与 spec 编号**各自独立**，互不占用。

## 格式

用 `docs/decisions/_template.md`。四段必须齐：

- `## 背景`：当时的事实与约束（不是事后叙事）
- `## 决策`：一句话说清选了什么
- `## 备选`：表格，每个备选写「为什么不行」——空着等于没写
- `## 后果`：接受了什么代价、什么情况下应该重新考虑

标题下面三行元信息：`> 状态:`（proposed / implemented / rejected）、`> 日期:`、`> 关联:`（spec 编号）。

## 什么时候必须写

- 改了架构形状（传输、存储、部署）
- 拒绝了看起来更简单的方案（尤其是「加个端口」「加个依赖」这类）
- 一个取舍会反复被问到（成本、隐私、兼容）

## 什么时候不要写

- 只有一个选项的改动
- 纯实现细节（变量名、拆函数）
- 还没想清楚的猜测——放 `docs/implementation/log/` 里当事实记录，想清楚再升级成 ADR
