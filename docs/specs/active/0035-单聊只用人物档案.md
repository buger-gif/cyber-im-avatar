# 0035 单聊只用人物档案：一份文件，不再套两层

> 状态: 实施中
> 编号: 0035
> 版本: 0.15.0
> 关联: `docs/specs/contracts/01-api.md`、`docs/specs/contracts/02-storage.md`、
> `docs/decisions/implemented/0008-画像按人和会话拆两层.md`

## 背景

0.14.1 起画像按「人」和「会话」拆两层：`profiles/people/<platform>/<person_id>.md`
（人物档案）与 `profiles/<platform>/<chat_id>.md`（会话工作本）。这套划分对群成立——
群规、回复口径、成员角色不属于任何一个成员；对私聊则是重复的：

- 私聊里「这个会话」和「对面这个人」是同一件事，工作本与人物档案写的是同一批事实；
- 插件在「加入值守」时仍 `ensure` 私聊工作本，于是每条私聊留下两份 md；
- 唤醒载荷对私聊同时给「会话工作本」与「人物档案」两条路径，agent 每轮要在两份文件里
  判断写哪一份；面板人物卡片的「私聊工作本」入口点开后没有编辑区（`personBookEditor`
  从未被调用），形同摆设；
- 用户原话：「单聊模式 不要搞两层md了，单聊直接用目标人的md就好了 你搞两层 多余」。

群仍然需要两层：同一个人在多个群与私聊里反复出现，群规只属于群。

## 目标与非目标

- **目标**：私聊只剩一份 md——对方的人物档案；插件不再创建、不再展示、载荷不再给私聊
  会话工作本；已有旧工作本不丢内容；群的两层行为不变。
- **非目标**：
  - 不改轮询节奏、唤醒成本模型、会话状态机、`state.json` 形状（不加字段、不升 version）；
  - 不改群的两层划分与群载荷；
  - 不自动做语义拆分（把旧工作本的段落拆进人物档案各节）；只做整文件搬运，归并交给 agent；
  - 不解决钉钉 `senderId` ≠ `userId`：推不出人物 ID 时沿用旧行为（会话工作本），不猜人；
  - 不加第三方依赖、不监听端口。

## 方案

### 1. 私聊的记忆文件就是对方的人物档案

| 会话 kind | 记忆文件 | 载荷 |
| --- | --- | --- |
| `p2p`，能推出人物 ID | `profiles/people/<platform>/<person_id>.md` | 一行 `人物档案：<绝对路径>`，不再列人物档案块 |
| `p2p`，推不出人物 ID（钉钉等） | `profiles/<platform>/<chat_id>.md`（旧行为） | `会话工作本：<绝对路径>` |
| `group` | 两层：工作本 + 各发言人人物档案 | 与 0.14.1 相同 |

- 人物 ID 的推导沿用 `chatPersonId`：优先最近一条非本人消息的 `sender_id`；没有消息时按
  平台形态用 `chat_id` 兜底（飞书 `ou_` / 企微单聊 `chat_id`＝`userid` / 钉钉不兜底）。
- 私聊独有的要求（「只在企业微信找她」这类）也写进这份档案：用「私聊：」前缀标明，
  群上下文读到时知道那是单聊口径。人物档案的四段模板不变，跨形态仍是同一份。
- 插件只做确定性推导与搬运：不读正文、不拆段、不判断归属。

### 2. 唤醒 / 开场 / 心跳载荷

- 私聊：`人物档案：<路径>（单聊只维护这一份：这个人是谁、怎么说话、在意什么、历史结论；
  只在这条私聊成立的备注也写这里，用「私聊：」开头）`，不再出现 `会话工作本：`，
  也不再有 `人物档案：` 多行块（同一个人不重复给两次路径）。
- 群：与现状一致（工作本一行 + 本批发言人档案行）。
- 私聊旧工作本还没并进来时，每轮多一行（文件消失即停）：
  `旧私聊工作本（待并入）：<路径>（…把仍然成立的内容并进去，再把旧文件改名为 <…>.history.md）`。
- 心跳对私聊只整理这一份档案；群的「工作本 + ≤3 份档案」不变。

### 3. 旧私聊工作本：整文件搬迁，不丢内容

- 第一次被面板或加入值守碰到（`/api/targets`、`/api/watch`、`/api/chat/mode` 走到
  `ensureMemory`）时：
  1. 人物档案不存在、旧 `profiles/<platform>/<chat_id>.md` 存在且有内容 → 把旧文件
     **原样搬进**人物档案路径（复制成功后删旧文件；不改写一个字，不做语义拆分）；
  2. 旧文件是没写过内容的模板（与工作本模板逐字节相同）→ 删掉它，按人物档案模板重建，
     不留第二份；两者都不存在也建人物档案模板；
  3. 人物档案已存在、旧工作本还在 → 不动旧文件，交给 agent 按载荷的「待并入」行合并并归档。
- 复制用排他创建（COPYFILE_EXCL）：另一路刚好写好人物档案时不覆盖它；搬完再删旧文件，
  删不掉就回滚这次复制，避免两份并存。旧内容一字不丢，第一次打开面板就能看到。agent 下一次处理该私聊时按
  `SKILL.md` 把它整理成人物档案四段，旧全文归档 `.history.md`。
- 回滚代价：搬迁后旧路径不存在；回滚代码后内容仍在人物档案里，只是路径换了（见§风险与回滚）。

### 4. 接口与面板

- `GET /api/targets`：p2p 能推出人物 ID 时，`profile` / `profile_excerpt` / `profile_path` /
  `profile_updated_at` 指向人物档案（并 `ensure`：先按第 3 节搬旧文件，再补模板）；
  `person` 块照旧给出同一路径。推不出 ID 时字段仍指会话工作本。群不变。
- `POST /api/targets/profile`：p2p 写人物档案（同一份文件），群写会话工作本；`chat_id`
  优先、`name` 兼容旧面板的逻辑不变。
- `DELETE /api/forget`：仍只删旧会话工作本与会话状态；人物档案跨会话保留（删人物走
  `DELETE /api/persons`）。
- 面板：人物卡片删掉「私聊工作本」按钮与被删掉的死代码；「群聊」段只列群与推不出人物
  ID 的私聊兜底；文案统一成「单聊只有一份人物档案，群才有会话工作本」。
- 契约：`docs/specs/contracts/01-api.md`（`/api/targets`、`/api/targets/profile` 语义）、
  `02-storage.md`（§画像文件 的 p2p 单层与旧文件搬迁）。

### 5. 独立 skill 形态

- `scripts/bootstrap.py` 注册搜到的人（`kind=user`）时写 `person_id`，`profile_file`
  指向人物档案；`ensure_profile` 对带 `person_id` 的目标用人物模板，并在人物档案不存在时
  把旧工作本整文件搬过来。
- `--note` 对这类目标写进人物档案；`--person-*` 不变；群与 `--alias` 手填目标不变
  （没有人物 ID 就走工作本，不猜）。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 私聊继续两层、只是面板隐藏工作本 | 文件与载荷仍然两套，agent 每轮还是要判断写哪份；用户要的是少一份文件 |
| 群也合成一份 | 群规/工作要求与成员评价是两种生命周期；多个群遇到同一个人又要复制评价（ADR 0008 的结论） |
| 旧工作本用脚本按语义拆进人物档案四段 | 归属判断会错；脚本拆是静默错归因，违反「不替你说错话」 |
| 旧工作本直接删、让 agent 重建 | 内容丢失，面板第一眼看不到旧结论 |
| 给 `state.chats` 加 `person_id`，注册时记下 | 要升 state 版本；消息到达后 `recent[].sender_id` 已够推导，钉钉的真机映射仍未定 |
| 人物档案里再分「私聊 / 群」两节 | 同一件事在群里可能也成立；用「私聊：」前缀足够，别把模板长成两层 |

- **代码**：`dsh-plugin/lib/profiles.js`（单聊记忆解析、旧文件搬迁）、`lib/turns.js`
  （三类载荷）、`lib/app.js`（targets / 写档案 / 加入值守的记忆文件）、
  `web/panel.js` → 重建 `lib/client.js`；`scripts/bootstrap.py`（搜人注册与 `ensure_profile`）。
- **契约**：`docs/specs/contracts/01-api.md`、`02-storage.md`；不改配置键。
- **文档**：`SKILL.md`（两份副本）、`README.md`、`dsh-plugin/README.md`、
  `docs/architecture/02-data.md`、`03-runtime.md`、`01-shape.md`、
  `references/{feishu,wecom,dingtalk,troubleshooting}.md`、ADR 0009、`CHANGELOG.md`。
- **用户可见**：私聊不再生成第二份 md；面板人物卡只看一份档案；旧私聊内容第一次被碰到时
  自动搬到人物档案（原文不变），agent 下一次处理时整理成四段。
- **兼容**：旧 `profiles/<platform>/<chat_id>.md` 不删不改写（搬迁除外）；群行为逐字节不变；
  面板旧字段名保留；不改 `state.json`；回滚不需要清库。

## 风险与回滚

- **风险：12KB 上限更容易撞。** 私聊把渠道备注也写进人物档案，档案增长更快；仍按 8/12KB
  与心跳整理兜底，超限拒写并如实报错。
- **风险：搬迁与 agent 正在写人物档案并发。** 只在该私聊第一次被面板/值守碰到时做一次；
  用排他复制，目标已存在就放弃（保留旧文件，载荷仍给「待并入」路径）。
- **风险：钉钉私聊继续用工作本。** 这是未验证映射的既有降级，不是新回退；真机确认
  `senderId` = `userId` 后再放开。
- **已知边界：私聊最近 10 条全是本人消息时推不出对方。** 飞书 `oc_` 形态的私聊会暂时退回
  工作本兜底；对方再说话后回到人物档案，多出的工作本按「待并入」由 agent 合并归档。
  不要把显示名或聊天里出现过的任意 ID 当对方（那会静默写错人）。
- **回滚**：撤掉这个 commit；已搬进人物档案的内容完整，只是路径从
  `profiles/<platform>/<chat_id>.md` 变成 `profiles/people/<platform>/<person_id>.md`；
  需要旧路径时手动移回，内容不丢；不需要清 `state.json`。
