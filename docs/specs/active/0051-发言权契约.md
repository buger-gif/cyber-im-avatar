# 0051 发言权契约：事实进载荷，授权进工作本

> 状态: 待实施
> 编号: 0051
> 版本: 0.24.0
> 关联: `docs/decisions/implemented/0016-发言权契约.md`、`docs/specs/contracts/01-api.md`、`docs/specs/contracts/03-config.md`

## 背景

2026-11-18 飞书值守事故：某值班机器人在群里 @ 的是处理人，值守账号是同一个群的
跟进人，`send_mode=auto`，agent 在**开场轮**以跟进人身份代处理人回了进展。

本次取证纠正了当时的判断：插件侧的 @ 识别是对的——那条消息被存成 `kind=fyi`、
`skip=no-mention`，`probeForDuty` 里的 `anyMention` 为假，`duty.trigger` 因此仍是 `added`。
错在开场轮：载荷写的是「有该回的就按 skill 回」（开放式邀请），又没给本人身份，
当时工作本还是空模板，agent 无从知道「我在这群是谁、什么该我管」。

同时确认另一面：收紧成「只 @ 我就回」不能要——新建群经常没有任何 @，但任务确实落在
本人身上。注意力（省 token 的启发式）与发言权（正确性）被绑在 mention 一个信号上，
收紧就漏、放松就错。

现状读数（本机）：314 个会话、32 个 `send_mode=auto`；`config.send_mode_default=auto`。

## 目标与非目标

- 目标：每个群有一份可读、可改、可复用的「我在这个群的发言权」；插件把判断需要的事实
  （本人身份、谁被 @、本批是否点你名）给足，不再给结论；契约未定义时该群不出全自动。
- 非目标：不做发送拦截（做不到，见 `docs/decisions/implemented/0016-发言权契约.md`）；
  不新增关注程度档；不做决策文件；不把正文或判断落进插件状态。

## 方案

### 1. 契约落在工作本的一个固定小节

`profiles.profileTemplate()` 新建群工作本时带上标题（body 为空）：

```markdown
## 我在这个群的发言权

- 我是谁：
- 该我回：
- 不该我回：
- 别人被点名时：
```

- 结构化判定：`rightsSection(text)` 取标题行到下一个 `## ` 行为止的 body，去空白后非空
  = `defined`。标题被删也算未定义（fail-closed）。
- 只对群生效；私聊不看契约（对方在跟你说话，规范显然）。
- 判断是结构性的，不解析语义（铁律 8）。

### 2. 未定义 → 本轮最高草稿

`turns._wake()` 里按会话读一次工作本，群且 `!defined` 时把本轮 `sendMode` 降为 `draft`，
载荷声明改为：

```
发送方式：草稿审批（本群发言权未定义，全自动暂停；写进工作本「我在这个群的发言权」后自动恢复）
```

契约写好后自动恢复 `auto`——依赖关系，不是开关，不加配置键、不改 `state.json`。

### 3. 载荷从「结论」改成「事实 + 指针」

| 现在 | 改成 |
| --- | --- |
| `值守判断：watch（只盯 @我）` | `本群今天自动转入值守`（只留事实） |
| `只盯 @我：非点名的群消息不需要处理。` | 删掉：mention 模式下非点名消息根本不会进批次，结构上已成立 |
| `全量模式：非点名的群消息只看不回…` | `本批 N 条点你名，其余是知会；默认沉默，按发言权契约判断。` |
| `有该回的就按 skill 回，没有需要回的就不要往群里发消息。` | `默认动作是沉默；要发言先能回答「为什么是我」，并把口径写进契约。` |
| `判断口径：个人 @ + 具体请求 → watch` | `点你名（mention.id == 本人 open_id）+ 具体请求 → watch` |

新增事实行（首轮 / 开场轮）：

- `本人：<name> · <platform> · open_id <id>`（取 `poller.identity`，取不到就省略，不猜）
- 每条消息行标出被 @ 的人：`- [10:30] 值班机器人（@周明）: …`；`（@你）` 保留
- `本批 0 条点你名。`（batch 级，群）

开场轮额外一段「先写契约再决定」的任务说明；`buildDeskPrompt` 同样给身份与
「本批 N 条点你名」，判断口径同步改成「点你名」。

### 4. 面板怎么改这一刻

**只暴露这一段，不做整本编辑**：工作本里还有 agent 的知识（群内工作要求 / 成员与角色 /
结论），整本编辑会让人有机会覆盖它们，职责也模糊——**人是授权方，agent 是知识方**。

- `GET /api/rights`（`platform`、`chat_id`）→ `{ok, exists, defined, text, body, path, mtime, title}`
- `POST /api/rights`（`platform`、`chat_id`、`text`、`base_mtime`）：只替换该小节 body，
  **其余字节一个不改**；`base_mtime` 与磁盘不一致回 `stale`（沿用 0050 的模型）；
  `text` 为空 = 清空该小节（回到未定义）；标题不存在时在文件末尾补回；上限 8KB；原子写（`600`）。
- `/api/targets` 的群行补 `rights_defined` / `rights`（该行本来已经读了工作本全文，
  零额外 I/O），面板卡片据此显示 `发言权 未定义 · 全自动已暂停`。
- 编辑器沿用 0050：`base_mtime` 冲突 → 保留草稿、取最新 mtime、再点一次才覆盖。

### 5. 所有权

- 开场轮：未定义时由 agent 写第一版（它是唯一知道群上下文的人）。
- 已定义：agent **只读**，不改；用户要求改才改。
- 人可以随时在面板改；这就是控制点。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 契约放独立文件 | 工作本已有「群内工作要求 / 成员与角色」，同一份规范长两处；多一条指针行，还多一个可能过期的读点 |
| 面板整本编辑工作本 | 会覆盖 agent 的知识段；且没有单一「授权边界」的可见形态 |
| 把 `defined` 塞进 `state.json` | 契约是文件内容，状态里再存一份就是双源，agent 改文件后状态会漂 |
| 未定义时直接禁止启值守 | 违背「新群没 @ 也值得盯」的事实；草稿已经够了 |

  `duty.js` 的 `DEFAULT_POLICY`（默认沉默）、`docs/architecture/03-runtime.md`

## 风险与回滚

- 风险：老群一夜之间全部降为草稿（契约段历史为空），用户觉得「怎么都要确认了」。
  这是有意的 fail-closed，面板卡片要写明原因与一句话入口；补一次即恢复。
- 风险：agent 整文件写工作本时覆盖掉人刚改的契约段。缓解：SKILL 明确「写前重读、只增量改」，
  且契约段已定义时 agent 不改写。
- 回滚：撤 spec 0051 的提交即可；无数据迁移、无配置键，`state.json` 不需清理。
