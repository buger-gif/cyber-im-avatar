# 0034 单轮停滞超时

> 状态: 实施中
> 编号: 0034
> 版本: 0.14.0
> 关联: `docs/specs/contracts/03-config.md`、`dsh-plugin/lib/turns.js`

## 背景

2026-11-05 上午值守的一个飞书私聊（真机，本机 state）连续两轮被整轮取消：

- turn 8：10:27:58 起，10:37:58 被取消，正好 **600 秒**；取消前 2 秒还在跑 `tool/call`（step 55/56）。
- turn 9：10:39:17 起，10:49:17 被取消，正好 **600 秒**；取消前 11 秒还在跑 `tool/call`（step 45/46）。

两轮的 DSH 会话日志都是 `turn/end reason={kind:"aborted",reason:{kind:"user"}}`——这个 `user`
是插件 `TurnManager.cancelHandle()` 传的 cancel cause，不是人在 DSH 里点中断；同一时刻插件
`state.json` 的记录是 `last_turn={ok:false,reason:"timeout"}`，与 `dsh.timeout=600` 的守卫表
（`runTurn` 里从轮次开始计时的单枚墙钟 `setTimeout`）完全对上。

结论：**表不是打在卡死上，是打在了活着的长轮上**。这两轮都是重活（跨系统调研 + 长回复），
10 分钟干不完是常态；被砍掉后 agent 正在写的回复直接丢。

另有一个观感问题：取消发生后 `pendingCount=0`（对方消息已被本人身份发出的消息标成 replied，
本人指令 `cmd` 本身不算待回），`maybeWake()` 的失败重试要求 `pendingCount>0`，所以**不会自动
重开**，只能靠人再发一条把它叫起来（本次是 10:59:46 手打「你继续干完吧」）。本轮不改重试策略，
见「非目标」。

## 目标与非目标

- 目标：`dsh.timeout` 从「单轮总时长上限」改成「**停滞超时**」——同一个 turn 里每收到一条
  该会话的 `session/event` 就重置计时；连续这么久一条事件都没有，才判定卡死并取消。
- 目标：新增总时长兜底 `dsh.turn_cap_sec`（默认 3600 秒，`0` = 不设上限），防止真卡死或死循环
  让一轮无限跑。
- 目标：取消原因分得开：停滞取消记 `timeout`，总上限取消记 `turn_cap`（面板/`last_turn`
  可直接看出是哪一种）。
- 非目标：不改「新消息到达即打断在飞 turn」的语义；不改 `allowCmdWake` 熔断。
- 非目标：不做超时后的自动续跑 / 自动重试（涉及 token 预算与循环保护，另开 spec）。
- 非目标：不改 `agent.cancel` 的 cause（仍是 `{kind:"user"}`，DSH 侧显示口径另说）。
- 非目标：不改 prompt、state 结构、路由、`msg` / `chat` 字段。

## 方案

### 1. 看门狗（`dsh-plugin/lib/turns.js`）

新增模块级纯逻辑 `turnWatchdog({ stallSec, capSec, onTimeout })`，`runTurn` 用它替换原来的
单枚墙钟定时器：

- `start()`：启动停滞计时，并按 `capSec > 0` 启动总上限计时（从本轮开始算）。
- `touch()`：**每个该会话的 `session/event` 调一次**，只重置停滞计时；总上限不受影响。
- 先到先触发一次：停滞 → `onTimeout("timeout")`，总上限 → `onTimeout("turn_cap")`。
- `stop()`：`settle()` 时调，两枚计时器都清掉；触发后也不再重复触发。
- 计时器 `unref()`，不拖住宿主退出。

`runTurn` 侧改动：删掉原来的单枚 `timer`；在 `session/event` 监听里先 `watchdog.touch()` 再
`collect(event)`（监听器已按 `agent.session` 过滤）；`onTimeout` 复用原超时分支
（`handle.cancelled=true`、`handle.timedOut=true`、`cancelHandle()`、`finish({ok:false,reason})`）。

事件粒度依据（真机读数）：该会话同一 turn 内相邻事件最大空档 61.6 秒（另有一次 60 秒的
`job/registered → tool/result` 等待），远小于默认 600 秒停滞阈值；改成停滞语义后正常长轮不会再被切。

### 2. 配置（`dsh-plugin/lib/state.js` + 契约 03）

| 键 | 默认 | 取值 | 说明 |
| --- | --- | --- | --- |
| `dsh.timeout` | `600` | 120–3600 秒 | **停滞**超时：这么久没有任何会话事件才算卡死；有活动会不断重置 |
| `dsh.turn_cap_sec` | `3600` | 0–86400 秒 | 单轮总时长兜底；`0` = 不设上限 |

- `dsh.timeout` 下限从 30 抬到 **120** 秒：真机最大事件空档已到 61.6 秒，30 秒的停滞阈值会
  误伤正常工具等待；抬下限对存量只放宽（30/60 会被夹到 120，取消得更少，不会更频繁）。
- 同 commit 改 `docs/specs/contracts/03-config.md`（键表 + 夹取范围表），
  `tests/test_docs.py` 的 `RANGE_KEYS` 加 `dsh.turn_cap_sec`，`tests/state.test.mjs` /
  `tests/migrate.test.mjs` 里 `dsh.timeout` 的夹取断言从 30 改 120。

### 3. 面板（`web/panel.js` + 构建产物）

设置页「单轮上限」一行改成：「停滞 X 秒 · 总上限 Y 秒 · 新消息到达会打断在飞 turn」，
总上限为 `0` 时显示「不限」。改完 `python3 scripts/build_client.py` 重建 `lib/client.js`。
不加输入框：本轮只修口径，改值走 `/api/config` 或 `state.json`。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 只把默认值 600 调大 | 重活多长都可能超，调大又让真卡死等更久，两头不讨好 |
| 完全去掉超时 | 真卡死会永久占住会话，人在面板上也没有「这轮还在跑」的真相 |
| 「有未完成的工具调用就不算停滞」 | DSH 事件粒度已经够用（最大空档 61.6 秒），多一层状态只增加边界 |
| 超时后自动续跑 | 用户本轮只要求修「被误杀」；自动续跑牵扯 token 预算与循环保护，另开 spec |
| 只改代码不加配置键 | 总上限必须有兜底且可调；写死 3600 会让超长任务没法放开 |

## 风险与回滚

- 风险：单个工具阻塞很久（> `dsh.timeout`）期间没有任何会话事件 → 仍会按停滞取消；这与改动前
  的总时长上限相比不会更差，且总上限 `turn_cap_sec` 可再兜底。
- 风险：事件很密时每个事件都 `clearTimeout + setTimeout`，成本可忽略（每轮最多几百次）。
- 回滚：revert 该 commit；已写入 state 的 `dsh.turn_cap_sec` 在旧代码里被忽略，没有迁移、
  不需要清数据。
