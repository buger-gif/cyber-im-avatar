# 0024 群聊关注程度

> 状态: 待实施
> 编号: 0024
> 版本: 0.10.0
> 关联: `docs/specs/contracts/01-api.md`、`02-storage.md`、`03-config.md`

## 背景

群现在只有「拉不拉」一个维度（`timer`），唤醒策略写死在代码里：只有被 `@` 的、且仍是
`new` 的那条消息会进唤醒批次。面板上「值守」与「定时检测 @我」又是两个独立开关，
组合出四种状态，实际踩到的是这两种：

- 值守开了、定时没勾：看起来在盯，其实一条都不拉。群默认 `timer=-1`（点开才拉），
  没勾就不会有任何新消息进来。
- 事后才打开值守：之前那几条 `@` 已被点开（`opened`）或清理（`ignored`），而唤醒批次
  只收 `new`——自动通道永远不会再叫醒它，只能按「现在处理」手动补跑。

真实读数（2026-11-03 某群）：17:33 / 17:34 两条 `@` 未唤醒，17:36 手动「现在处理」
才起 turn。这不是偶发，是开关形状本身会让人踩。

## 目标与非目标

- 目标：群值守收敛成一档「关注程度」三选一——`不盯` / `只盯 @我` / `全部消息`；
  「全部消息」下非 `@` 消息也进唤醒批次，但只**看**不**回**，要本人表态的进当日日报等拍板。
- 非目标：不做关键词模式；不做跨群聚合；不改私聊行为；全量模式不主动往群里发消息。

## 方案

### 1. 存储：三个新字段（契约 02）

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `wake_mode` | string | `"mention"` | 群唤醒策略：`mention`＝只 `@` 唤醒；`all`＝非 `@` 也唤醒。私聊恒为 `mention`，不读 |
| `last_wake_at` | number | `0` | 上一次成功唤醒的墙钟时刻（epoch 秒），用于合并窗口 |
| `last_wake_epoch` | number | `0` | 上一次唤醒批次里最大的 `ts_epoch`，用于去重、不重复投递 |

迁移只放宽：老 state 没有 `wake_mode` 一律补 `mention`，等价于现状；`timer` 语义不变
（群默认 `-1`）。老数据加载后不会突然开始唤醒。

### 2. 分类与正文（契约 02）

`wake_mode === "all"` 的群：

- 非 `@` 消息仍标 `kind: "fyi"`（载荷里能分清点名与否），但 `state` 记 `new`，进待回；
- 正文保留规则从「仅 `new`/`opened` 的 `dm`/`mention`/`service`」放宽为「仅 `new`/`opened`
  的非 `out`」。正文仍只在本机落盘，不上传、不进日志。

`mention` 模式完全沿用现状：`fyi` 直接 `ignored`，不唤醒。

### 3. 唤醒批次与合并窗口（契约 03）

新增配置 `poll.group_wake_sec`，默认 `60`，取值 `0`–`3600`：

- `all` 模式下同一群每 `group_wake_sec` 秒最多唤醒一次，窗口内的消息留在本地等下一轮；
- 批次＝该群 `state=new` 且 `ts_epoch > last_wake_epoch` 的待回行（`dm`/`mention`/`service`
  ＋全量模式下的 `fyi`），上限 **30 条**，超出写「另有 N 条」；
- 唤醒成功即写 `last_wake_at`（墙钟）与 `last_wake_epoch`（批次最大 epoch）；失败不动，
  下一轮重试；
- 快车道仍是 60 秒一轮，所以默认值等价于「每分钟最多一次」，与私聊节奏一致；
- `mention` 模式不受窗口影响，保持「本轮新到 + `new`」。

### 4. 载荷（契约 01 的 agent 侧约定）

`wake_mode=all` 的每轮载荷末尾追加一行固定说明，不改其它上下文：

> 全量模式：非点名的群消息只看不回，要本人表态的写进当日日报等用户拍板；
> 标了「（@你）」的消息照常处理，该回就回。

首轮把模式说明并进现有的形态段，不注入画像正文。点名是事实不是判断：`kind="mention"`
的消息行在发送者后面标「（@你）」，全量模式下 agent 不用猜哪条该回。

### 5. 面板（契约 01）

- 群详情头部与「服务」页群卡片：把「定时检测 @我」开关换成一个三态控件
  `不盯` / `只盯 @我` / `全部消息`；
- 新路由 `POST /api/chat/mode {platform, chat_id, mode}` 一次写三个字段：

| mode | watching | timer | wake_mode |
| --- | --- | --- | --- |
| `off` | false | -1 | `mention` |
| `mention` | true | 1 | `mention` |
| `all` | true | 1 | `all` |

- `publicChat` 暴露 `wake_mode` / `last_wake_at`；设置页多一个窗口输入框。
- 群从任何入口加入值守（`/api/watch`）默认落「只盯 @我」：`timer=1`、`wake_mode=mention`。
  不这么做会留成「值守中但 timer=-1」——看着在盯、其实一条不拉，就是这次问题的原形。
  「全部消息」只能显式选，不会因为加入值守而默认打开。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 复用 `timer` 的 -1/0/1 承载三态 | `timer` 是「拉不拉」，唤醒策略是另一维；塞进去私聊语义被迫变形，老数据也解释不清 |
| 全量模式每条都唤醒 | 活跃群一小时 60 次模型调用；合并窗口是确定性节流，属于插件职责 |
| 全量模式自动回复 | 群里刷屏时容易替本人说错话，与「宁可不回也不乱回」冲突 |
| 顺手加关键词模式 | 现在没有真实需求；独立 skill 已有 `--keyword`，插件侧等有人要再加 |

## 验收

- [ ] 老 state.json（无 `wake_mode`）加载后 `wake_mode==="mention"`、`last_wake_at===0`，群仍不轮询
- [ ] 群设 `all` + `timer=1`：一条非 `@` 消息 → `state=new`、正文保留、唤醒一次
- [ ] 同一轮里混一条 `@` → 载荷里标「（@你）」并带「照常处理，该回就回」的规则行
- [ ] 同群 `group_wake_sec` 内再来两条非 `@` → 不唤醒；窗口过后一轮把积压合并成一次唤醒
- [ ] 唤醒成功后同一批消息下一轮不重复投递
- [ ] 群设 `mention`：非 `@` 仍 `ignored`、不唤醒（回归）
- [ ] 面板切到「全部消息」→ `/api/chats` 读到 `watching=true, timer=1, wake_mode="all"`
- [ ] 群勾「值守」加入 → `timer=1`、`wake_mode="mention"`（默认只盯 @我，不会默认全量）
- [ ] `node --test`、`python3 tests/run_tests.py`、`bash scripts/gate.sh --quick` 全绿

## 风险与回滚

- 风险：全量模式配大群会显著抬高 token；窗口与 30 条上限只压制、不消除。
- 回滚：面板把群切回「只盯 @我」即时生效，字段留在 state 里不读即可；代码下 revert 单个
  commit，新字段是纯增量，老数据不用清。
