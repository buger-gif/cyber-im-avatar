## 背景

桌面端用 `dsh-app://app/` 打开界面：index 由桌面壳从打包的 dist 直接读，宿主启动时通过
一次 IPC（`ready.injections`）把 `webserver/index-inject` 的快照交给页面（DSH 0.2.2-rc.5，
`lib/main.js` 的 `serveWebDocument` / `forwardWebRequest`）。插件宿主的 `x-im-token` 是
模块级随机值，改动插件代码触发 HMR 重载就会换一个；桌面壳不会重取快照，页面刷新也只是
把旧快照再注入一次——所有面板接口 401，横幅提示「会话凭据过期」，而生产包没有绑定 ⌘R
（刷新菜单只在开发模式出现）。

2026-11-26 实测：页面 13:34:44 加载，宿主 13:48:40、15:10:35 各热重载一次
（`~/.im-standin/logs/boot-inject.jsonl` 的 `host-apply`）；之后刷新没有产生新的 index
请求/注入（同文件无 `inject`，`client-boot.jsonl` 无新的 `client-apply`）。值守轮询本身
正常：15:33 那轮 9 个会话、26 个目标，15:37 还有唤醒。

## 目标与非目标

- 目标：插件热重载 / 宿主重启后，已打开的面板不刷新也能继续调接口。
- 非目标：不改 DSH 本体；不改路由；不把 token 落盘；不降低「同机其它页面不能读面板」的边界。

## 方案

面板鉴权认两种同一性：

1. `x-im-token` 等于当前进程的随机 token。保留给没有 DSH cookie 的旧页面、直连预览和
   没有 `connection` 服务的宿主。
2. 通过 DSH 自己的浏览器会话：`connection.requestRejection(req) === undefined`。
   桌面壳每次转发都带宿主签发的签名 cookie，浏览器同源页面也自动带；热重载、宿主重启、
   页面刷新都不影响。`requestRejection` 与插件现有检查叠加，仍要求回环连接、Host 回环、
   Origin 同源。

顺序：先比 token，不匹配再问 DSH；`connection` 不存在、`requestRejection` 缺失或抛错时
退回只用 token。判权收成纯函数 `dsh-plugin/lib/panel-auth.js`，`lib/index.js` 只接线：

```js
const auth = requestAuthorized(req, TOKEN, connection);
if (!auth) return send(res, 401, { error: "not authenticated; refresh or reopen" });
```

面板 401 文案改为「面板会话失效，刷新页面或重开窗口再试」，不再承诺 ⌘R。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| token 改用进程级全局值 | 只防住本次 HMR；宿主重启仍换 token，仍要重启桌面端，也治不了已经打开的页面 |
| 401 时把新 token 塞进响应头 / cookie 发回 | 等于给任何本机循环请求发凭据，弱化现有 token 的边界 |
| 直接调 `connection.browserAuth.isAuthenticated` | 内部字段，跨 DSH 版本会漂；`requestRejection` 是公开入口（`dsh-experimental-inspector` 同款用法） |
| 让桌面壳重取 injections | 改不了已安装的 DSH 本体 |

## 风险与回滚

- 风险：若某个本机入口能伪造 DSH 签名 cookie，面板边界会被绕过；签名与过期由 DSH 进程密钥
  负责，插件只做委托，不放大权限。Host/Origin 判定与插件现有三道检查叠加。
- 回滚：撤掉 `panel-auth.js` 的 DSH 分支（回到只认 token），不涉及数据。
