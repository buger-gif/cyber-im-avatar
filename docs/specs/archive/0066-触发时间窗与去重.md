# 0066 触发时间窗与去重记录

> 状态: 已验收
> 版本: 0.28.0
> 日期: 2026-11-27
> 关联: spec 0065、ADR 0021

## 背景

0065 上线后重载宿主，慢车道第一轮把 31 个值守会话的补读结果全当成新消息处理：19 秒内核对完
31 个会话，13 个会话各起一轮、宿主里新建 10 个 DSH 会话；用户随即暂停。事后读数：这 13 个
会话里最新的消息也都 ≥339 秒，最老 14.8 天——补读回放的是旧账，不是新消息。

两个缺口：区间读最多回看 2 小时（流 24 小时），且旧 state 没有 `seen` 环，水位之前的历史被
整窗重投。用户要求：**时间窗必须定死、不能超窗处理；触发过的消息要有记录，不能重复发。**

## 目标与非目标

目标：

- 自动触发只处理**最近 10 分钟**的消息；窗口外不建会话、不进批次，只留可查记录。
- 「触发过的消息」有持久记录，流 / 对账重读、重载后都不重复触发。
- 补读窗口与触发窗口一致，启动时不再一次性回放历史。

非目标：不补回旧 bug 在水位之前漏掉的 @（那正是风暴来源）；手动「现在处理」不受窗口限制。

## 方案

- `TRIGGER_WINDOW_SEC = 600`：`process` 只把 `ts >= now-600` 的消息当候选；窗口外的入站消息
  记 `state=ignored`、`skip="out-of-window"`，正文不落盘。本人指令 `cmd` 不受窗口限制。
- **不回溯水位**：`ts < chat.last_epoch` 的消息一律不分类（同秒消息仍靠 `seen` 放行）。
- **待投集合也收口**：`maybeWake` 先 `expireOutOfWindow()`，旧积压改成 `out-of-window` 留档；
  批次按时间倒序取，避免旧积压把新命中挤出 30 条上限。
- **触发记录**：`chat.seen` 保存最近 50 个见过的 `msg_id`（最新在前）；老 state 首次加载用
  `recent` 的 ID 播种。`recent[].delivered_at` 记「已交给 agent」，未投递的行不会被挤掉。
- **读窗口**：慢车道区间读、账号流回看都最多 10 分钟；更早记 `gap` / `truncated_at`。
- **兜底节流**：全局每分钟最多起 5 个会话，超出排队到下一跳；本人指令不排队。
- 面板：`skip` 标签加「超时间窗」，账号流读数显示「只处理最近 10 分钟」；`pollInfo` 暴露
  `trigger_window_sec`。

## 取舍

| 备选 | 为什么不行 |
| --- | --- |
| 只加「迟到 3 分钟不唤醒」 | 窗口没定死，5 分钟的旧账仍会一次拉起多个会话 |
| 保留 2 小时补读，只加节流 | 读本身就要 31 次、每次上百条；旧账仍会排队吵一晚上 |
| 回溯水位之前的历史补 @ | 正是 13 个会话风暴的来源；旧 bug 的漏 @ 交给面板记录与手动处理 |
| 不播种 `seen`，只靠 `last_epoch` | 同秒消息、重载边界仍可能重投；记录落盘才可查 |
| 把 5 个/分钟也做成配置 | 目前没有证据需要用户调；先固定，出现真实瓶颈再加键 |

## 验收

- [x] 单测：11 分钟前的命中不唤醒，记 `ignored` / `out-of-window`，正文清空，不进退回。
- [x] 单测：9 分钟前的命中照常唤醒；窗口外旧行不随新命中搭车。
- [x] 单测：只有旧积压的会话完全不唤醒；旧行被收口成 `out-of-window`。
- [x] 单测：旧 state 从 `recent` 播种 `seen`；水位之前的消息不重投。
- [x] 单测：全局每分钟最多 5 个会话，下一跳补投；区间读不按 per_chat_limit 截断。
- [x] 单测：流 / 对账重读同一 `msg_id` 不重复投递。
- [ ] 真机：水群刷 300 条后 @ 自己，120 秒内起 turn；重载宿主不出现批量起会话。
- [ ] 真机：停进程 10 分钟再启，只补最近 10 分钟，窗口外记录在面板可见。

## 风险与回滚

- 旧 bug 漏掉的 @（水位之前）不再自动补：面板有 `out-of-window` 记录，可手动拉；这是为了
  不再出现批量起会话，用户已确认取舍。
- 10 分钟窗口对「离线很久后最早的 @」意味着不叫醒；需要更长时间窗时改常量并补测试。
- 手动唤醒 / 「现在处理」仍不受窗口限制，属于用户显式动作。
