# 0031 人物档案与会话工作本：画像按「人」和「会话」拆两层

> 状态: 待实施
> 编号: 0031
> 版本: 0.14.0
> 关联: `docs/decisions/proposed/0008-画像按人和会话拆两层.md`、
> `docs/specs/contracts/01-api.md`、`docs/specs/contracts/02-storage.md`

## 背景

现在一个会话只有一份画像：`~/.im-standin/profiles/<platform>/<chat_id>.md`
（ADR 0004，spec 0012 / 0015 / 0018）。群聊和私聊用的是同一套四段：
对方是谁 / 沟通偏好 / 在意与忌讳 / 历史结论。

于是同一件事有两个落点、两个问题：

- **同一个人的评价被会话切开。** 在群里观察到的「张三要先结论」「张三不接受没时间点的
  回复」，写进了群画像；张三的私聊画像里没有。换一个群遇见张三，agent 还是不知道。
- **会话文件被人物评价淹没。** 群文件里真正属于「这个群」的内容——群规、什么该在群里说、
  回复口径、@ 习惯、谁负责什么——和成员个人评价混在一份文件里；文件越大，起草时越难
  抓到本会话的要求，整理时也越难判断哪条能删。

用户提出的划分：**人的评价维护在人自己的文件里；群里只放这个群的特殊要求和工作要求。**

以开发机为例（2026-11-05）：`state.json` 有 165 个会话登记、9 个服务对象
（7 个私聊 / 2 个群）、11 份画像文件（含 2 份 `.history.md`）。画像总量不大，
现在改存储形状的成本远低于养成几十份混装画像之后再拆。

## 目标与非目标

- **目标**：人物评价按「人」归一份，私聊与群聊共用；会话文件只保留本会话成立的
  要求与上下文；agent 起草一轮最多读 1 份工作本 + 少量人物档案；存量内容不丢、
  不强制迁移、升级前后值守行为不变。
- **非目标**：
  - 不改轮询节奏、唤醒成本模型、会话状态机；
  - 不改 `state.json` 形状（不新增字段、不升 `version`）；
  - 不写脚本自动拆分旧画像（归属是语义判断，脚本会静默错归因）；
  - 不做群成员自动索引（由 agent 在需要时用平台 CLI 查）；
  - 不解决钉钉 `senderId` ≠ `userId` 的完整映射（只记录双 ID + 合并规则，真机验收）；
  - 不加第三方依赖、不监听端口、不改独立形态监听引擎。

## 方案

### 1. 两层文件

```
~/.im-standin/profiles/
├── <platform>/<chat_id>.md            # 会话工作本（路径不变，内容重新划界）
└── people/<platform>/<person_id>.md   # 人物档案（新增）
```

- **人物档案**按平台人物 ID 一份：`person_id` 取消息里稳定的发送者 ID
  （飞书 `open_id`、企微 `userid`、钉钉消息 `senderId`），原样保留、不 lower、
  不用显示名。发送者 ID 为空（系统消息）不给档案路径。
- 文件名沿用现有 `safePart` / `_SAFE_RE` 规则（trim → 非法连续段替 `_` →
  去首尾 `._-` → 前 80 字符）；空 ID 直接跳过，不建档案。
- 目录 700、文件 600；写入走临时文件 + rename（沿用 `profiles.js`）；每份
  软上限 8KB、硬上限 12KB（超过拒写，不截断），`历史结论` >20 条或日期流水 >8 条时
  本轮必须整理，缩小时旧内容追加到 `<文件>.history.md`（沿用 spec 0015）。
- `people/` 放在 `profiles/` 子树下而不是 `~/.im-standin/` 顶层：`--delete-data`
  已经整树删除 `profiles/`，权限收紧、备份、隐私测试都只扩一处。
- 人物档案**不**引入 `env.json` / `profile_file` 索引：纯推导，避免独立形态
  （Python 认 `profile_file`）与 DSH 形态（Node 不读 `env.json`）路径分叉。

### 2. 内容归属（写哪里）

一句判据：**「换一个会话遇到这个人，这条还成立吗？」** 成立 → 人物档案；
只在当前会话成立 → 会话工作本；两边都成立 → 档案写结论，工作本只留指针或差异。

| 文件 | 四段 | 放什么 |
| --- | --- | --- |
| 人物档案 | 身份与角色 / 沟通偏好 / 在意与忌讳 / 历史结论 | 跨会话稳定的人物评价、称呼与忌讳、与我的往来和承诺 |
| 会话工作本 | 这个会话是什么 / 群内工作要求 / 成员与角色 / 本会话结论与待办 | 群目的与我的角色、群规与回复口径、@ 习惯、禁发事项、成员角色（名字 → 档案路径）、本会话待办 |

写作纪律：

- **一个事实只写一处**。工作本引用人物档案用指针（`张三 · 采购负责人 · people/feishu/ou_x.md`），
  不复制评价正文。
- **归因**：只把话记到 ID 能确认的发言人名下。转述、指代不明、匿名消息不写进个人档案，
  需要留就写在工作本并注明「未确认」。
- **隐私**：人物档案只写长期评价，不写聊天原文、一次性安排、凭据、群内敏感事件。
  可以读某人的档案来理解他，但不能把 A 群/A 私聊的上下文带到 B 会话的回复里。
- **冲突**：本人直接确认 > 私聊观察 > 群内转述；新结论推翻旧结论就改原句，
  不按轮次追加。
- **频率**：每轮最多 1–2 条人物档案更新、1 条工作本更新；没有「下次还会用到」的信息就不写。

### 3. 唤醒载荷：插件给路径，agent 判断

插件只做确定性推导，不解析画像、不注入正文：

- 对每个非本人消息发送者算出 `people/<platform>/<safe(person_id)>.md` 绝对路径；
- 首轮 / 开场载荷：

```
/cyber-im-avatar
值守命中 · 飞书 · 示例项目群 · 新消息
chat_id：oc_demo
运行形态：DSH 插件壳；监听、水位、唤醒由插件负责，不要挂监听。
会话工作本：/…/profiles/feishu/oc_demo.md（本会话的群规与工作要求；个人评价不写这里）
人物档案：
- 张三 · ou_demo_zhang → /…/profiles/people/feishu/ou_demo_zhang.md
- 李四 · ou_demo_li → /…/profiles/people/feishu/ou_demo_li.md
- [10:32] 张三（@你）：……
```

- 后续轮只追加本次消息行 + 本批新发言人的档案行；工作本行不重复。
  同一批里出现同名不同 ID 时，消息行标 ID 末 6 位，避免归因到错的人。
- 本批发言人最多列 5 个（@我 / 待回优先），其余按需用平台 CLI 查。
- 心跳轮给「工作本 + 最近 10 条里不同发言人的档案（最多 3 份）」，只整理列出的文件，
  不扫目录。
- 读取预算：工作本必读；人物档案默认只读要回复/被 @ 的那位（≤4 份），其余按需。
- **私聊的 `person_id`**：优先该会话最近一条非本人消息的 `sender_id`；没有消息时用
  `chat_id`（飞书 `ou_` 前缀、企微单聊 `chat_id`＝对方 `userid`；钉钉以真机结果为准）。
  两者都拿不到时只给工作本——退回旧行为，不猜、不静默造错档案。
- 不新增 `state.json` 字段：面板/插件需要 `chat_ids` 反查时直接聚合
  `state.chats[].recent[].sender_id`；人物列表扫目录。

### 4. 面板与接口

- 「服务对象」页分两段：**对象**（现有 target 会话，展示会话工作本）与
  **人物**（人物档案列表：名字取文件首个 `# ` 标题、摘要、更新时间、出处会话 chips）。
  人物支持编辑、删除、从平台搜人新建；编辑沿用现有 Markdown 预览 + textarea，
  增加 12KB 前置字节提示（超限不发请求）。
- 会话详情：私聊显示人物档案条（拿不到 ID 时退回工作本）；群显示工作本摘要 +
  本群人物 chips。文案统一为「人物档案 / 会话工作本」，不再出现「每个对象一份画像」。
- 路由（与 `docs/specs/contracts/01-api.md` 同 commit）：

| 方法 | 路径 | 入参 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/persons` | `platform`（可选） | 扫 `profiles/people/` 返回 items：`platform` / `person_id` / `name` / `profile` / `profile_excerpt` / `profile_path` / `profile_updated_at` / `chat_ids`。只读，不 `ensure`、不建空档案 |
| POST | `/api/persons/profile` | `platform`、`person_id`、`name`（可选）、`text`、`base_mtime`（可选） | 覆盖写 ≤12KB；`base_mtime` 与当前 mtime 不一致返回 `{ok:false, reason:"stale"}`，不写 |
| DELETE | `/api/persons` | `platform`、`person_id` | 删除一份人物档案（显式操作） |
| GET | `/api/targets` | — | 行保留 `profile*` 字段＝会话工作本；新增 `person`：p2p 能推出 ID 时给 `{person_id, path, excerpt, updated_at}` |
| POST | `/api/targets/profile` | 补 `chat_id`（优先，name 兼容旧面板） | 写会话工作本，仍是 ≤12KB |
| DELETE | `/api/forget` | — | 只删会话工作本与会话状态；人物档案跨会话保留，删除走 `/api/persons` |

- 面板只读目录；`GET` 不产生写盘副作用（现 `/api/targets` 的 `ensure` 保持原样，
  但人物列表不照抄）。

### 5. Skill 与独立 skill 形态

- `SKILL.md` 把「服务对象画像」一节就地重写为「两层记忆：人物档案 + 会话工作本」：
  归属判据、四段模板、读写时机、归因与隐私、上限与整理、旧画像迁移；
  首轮载荷、心跳、标准闭环、记忆清单、铁律「最小上下文」同步改。
- 独立形态给同等能力（agent 自己算路径，不依赖插件）：
  `scripts/bootstrap.py` 加人物路径/模板/追加/整理与 CLI
  `--person-path <platform> <person_id>`、`--person-note`、`--compact-person`、
  `--persons`（列表）；`--delete-data` 已覆盖 `profiles/` 整树，补断言。
- 双实现一致性：Python 与 Node 的 sanitize/path 用同一组 golden 向量测
  （中文 / emoji / 全角 / 控制符 / 空 / 超长 / 非字符串），断言同一字面路径；
  Node 侧保持不读 `env.json`，人物不使用 `profile_file`。

### 6. 存量迁移（懒迁移，不自动搬）

- 升级不改任何旧文件、不改 `state.json`；在 agent 第一次处理该会话之前，行为与旧版一致。
- 首次处理某会话（命中或心跳）：识别旧四段模板 → 拆分：
  1. 能确认 ID 的人物评价迁到对应人物档案（合并，不复制）；
  2. 工作本按新四段重写，只留会话级内容与成员指针；
  3. 旧全文先追加到 `<工作本>.history.md`，再覆盖写工作本（内容不丢）；
  4. 确认不了 ID 的条目留在工作本临时小节 `## 待归人物`，等该人再次出现时迁移；
     不再出现的条目保留在该小节，允许人工处理。
- 私聊：多数会话可直接从 `recent[].sender_id` 推出档案路径；迁移后工作本通常只剩
  渠道要求（如「只在企微找她」）。
- 群成员 ID 可用 `im +chat-members` / `contact +search-user` 解析；拆分的 CLI 调用
  计入当日日报的「本轮成本」，不拉全量成员。

### 7. 兼容与发布

- 不新增配置键；`dsh.full_access`、`warm_min` 语义不变，只改文案。
- 8KB/12KB 常量在 `profiles.js` 与 `bootstrap.py` 成对存在，两层各自一套、值相同。
- 目标是 0.14.0（MINOR：新增能力，旧数据与旧行为兼容）；CHANGELOG 记「未发布」，
  发版时再转版本小节。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 群画像里加「成员评价」小节 | 用户要的是人自己的文件；同一人在多个群/私聊之间仍然割裂，只是把混装挪了个位置 |
| 用显示名做文件名 | 重名、改名、同名不同人会串；面板按名字寻址的旧坑会原样复刻到人物层 |
| `~/.im-standin/people/` 顶层新目录 | `--delete-data`、权限收紧、备份、隐私测试都要多覆盖一处；`profiles/` 子树已够 |
| 插件维护 `state.people` 索引 | 双写会漂移，还得升 state 版本；列表扫目录 + `recent` 反查已够用 |
| 写脚本自动拆旧画像 | 归属是语义判断；脚本拆会静默错归因，而「不替你说错话」是项目底线 |
| 每轮唤醒都读全部人物档案 | 违反最小上下文；按本批发言人给路径、读被回复的那位即可 |
| 人物档案也走 `env.json` / `profile_file` 索引 | 独立形态（Python 认）与壳形态（Node 不认）路径来源不一致，已有分叉风险 |

## 风险与回滚

- **风险：agent 错归因，把 A 的话写进 B 的档案。** 载荷给 ID + 路径、归因纪律、
  写前重读；面板可直接改/删，发现即纠正。
- **风险：钉钉 `senderId` ≠ `userId` 产生双档案。** 档案头记录两个 ID 与来源；
  agent 发现同人双档时按合并规则并档；列真机验收项，不假装已解决。
- **风险：旧画像拆分丢内容。** 先追加 `.history.md` 再覆盖；拆分失败的会话保持旧文件不动
  （agent 下轮再试），不出现「拆一半」。
- **风险：人物档案跨会话累积更快撞 12KB。** 8/12KB 与 20 条结论限制、心跳整理、
  `.history.md` 归档；超限拒写会如实报错。
- **风险：面板覆盖 agent 刚写的内容。** 人物写接口支持 `base_mtime`，冲突返回 `stale`
  并提示「已更新，请重新加载」；agent 侧按 skill 写前重读。
- **回滚**：不改 state、不搬旧文件；回滚代码后旧工作本仍可读（被拆走的人物内容在
  `.history.md` 有全文）。不需要清数据。
