# 0065 刷屏不漏命中

> 状态: 已验收
> 编号: 0065
> 版本: 0.28.0
> 关联: `docs/specs/contracts/02-storage.md`、`docs/architecture/02-data.md §拉取节奏`

## 背景

### 1.1 两条不能猜的性质

- **P1 完整性**：平台在「上次读到之后」暴露的每条消息，要么被读到，要么留下一条显式的
  「这段没读到」记录，没有第三种状态。
- **P2 命中恰一次**：一条命中（@我 / 私聊来信 / 本人指令）最多叫醒一次；在**被投递之前**
  不因本地缓存淘汰而消失。

保证对象要收窄：**要一条不漏的是命中集合，不是全部消息**。群里的闲聊只需要一条「有缺口」
的记录；这是敢用一条账号级搜索兜底、而不逐条回放历史的前提。

### 1.2 现在怎么偏离的

1. **用采样代偿状态**：每轮取「最新 10 条」，回答的是「这 10 条里哪些我没见过」，不是
   「上次读到之后来了哪些」。刷屏超过 10 条时，窗口外的消息既没进 `recent`、也没进批次，
   水位却按最新一条推进——**这条消息从未存在过**。
2. **完整性靠猜**：不问平台「你读完了吗」，靠「窗口满 + 水位不在页内」推断。
3. **投递绑在扫描上**：批次 = 本轮扫描的新 id；晚发现的命中没有第二次机会，`recent` 只留
   10 条，未投递的命中会被挤掉。
4. **成本是 O(会话数)**：30 个值守会话 = 快车道每分钟 30 次拉取 + 慢车道每 10 分钟 30 次
   + 命令扫描 1 次/分钟 ≈ 4.9 万次/天；每次固定取 10 条，绝大多数是重复内容。负载和正确性
   被同一个「逐会话尾部采样」绑住了。

### 1.3 复现

假适配器：基线 m100，一分钟内 30 条，第 20 条 @我 → 只回最新 10 条（m121–m130），
`new=0`、`woke=false`，水位 1000 → 1030，`recent` 里没有这条，也没有任何错误记录。

### 1.4 平台实测（2026-11-27，只读、未打印正文）

| 事实 | 读数 |
| --- | --- |
| **账号级消息流可用**：`+messages-search` 不传 `--query`、只给时间窗，返回该窗口内**所有会话**的消息（p2p / group / topic / 卡片 / 本人消息都在） | 12–20 分钟窗口 49–102 条、13 个会话，`has_more` 可用 |
| **可以按会话收窄**：`--chat-id a,b,c`（逗号分隔）只回这些会话 | 32 个值守 id + 12 分钟窗 → 只回 1 条，且正好是未过滤结果里属于值守会话的那 1 条 |
| **完整性有信号**：`data.has_more` / `data.total` | 1 页 50 条时 `has_more=true`，收完为 `false` |
| **索引够新**：流里最新消息比插件上一轮逐会话拉到的还新 60 秒 | 同一 10 分钟窗，流 max - 插件 recent max = +60s |
| **线程/话题可见**：搜索结果里有 `chat_type=topic`（25/100 条） | 逐会话列表固定 `only_thread_root_messages=true`，看不到这些 |
| 单次延迟 | 1.8–2.5 秒（32 个会话过滤） |

结论：飞书能提供**一条账号级、可按会话过滤、带完整性信号、够新**的消息流。逐会话拉取不再是
唯一选择。

## 目标与非目标

- 目标：
  1. P1 / P2 成为结构性性质（完整性问平台，投递标记落在消息上）。
  2. **把请求量从 O(值守会话数) 降到 O(1)**，同时**不降低触发频率**（仍是 60 秒一跳）。
- 非目标：
  - 不改 60 秒下限与「发现 ≥10 分钟」的节奏（`AGENTS.md` 铁律 2）。
  - 不做事件订阅 / 长连接（看不到 user↔user 私聊，与「本人身份轮询」相反）。
  - 不把未值守会话的正文拉进进程（流必须按 `--chat-id` 收窄到值守会话）。
  - 不靠未读数决定叫不叫醒（把「要不要处理」绑到人有没有在手机上看过）。
  - 不为钉钉 / 企微发明它们没有的能力；没有账号流的平台走区间读，如实降级。

## 方案

一句话：**快车道从「逐会话尾部采样」换成「一条账号级消息流」；只有要唤醒时才读那一个会话。
慢车道退居对账。**

### 2.1 快车道：一条流（1 次/分钟，替代 30 次拉取）

```
lark-cli im +messages-search --as user
  --chat-id <值守候选的 oc_ id，逗号分隔>
  --start <stream_since - 2s> --end <now>
  --page-size 50 --page-limit 4 --page-all --no-reactions --format json
```

- **收窄范围**：只传值守候选（`candidates()` 的 `oc_` id，屏蔽的排除）。未值守会话的正文
  不进进程——和现在的可见范围一致。id 超过 100 个时分两批（当前 32 个，一批）。
- **平台分层**：这条流是飞书专属。企微保持逐会话区间读（有时间窗、没有跨会话搜索），钉钉
  保持采样 + 记账；三端不假装同一个实现。
- **本地分类**：按 `chat_id` 映射回会话，沿用现有 `process()` 的 kind 判定（`dm` / `mention` /
  `fyi` / `out` / `cmd`）；搜索结果缺 `reply_to`，引用原文与相邻上下文留给 2.2 的按需读。
- **游标 `stream_since`**：存 `runtime.stream`（丢了只丢 2 分钟，慢车道会对账）。成功 →
  `max(create_time)`（平台是分钟精度，天然带 ≤59 秒重叠）；窗口为空 → `now - 120s`（吸收
  分钟精度与索引延迟）；失败 → 不动游标，**当轮降级为逐会话区间读**补一次（宁可一次尖峰，
  也不静默漏），下一轮流恢复即回主路径；连续失败在面板红字。
- **完整性**：`has_more=true`（窗口内超过 200 条，只可能发生在停机补读）→ 追加一条
  `--is-at-me` 过滤搜索兜住 @，并记 `runtime.stream.truncated_at`；非 @ 的缺口靠慢车道对账
  （流是跨会话混合截断，无法归到某一个会话，所以不写单会话 `gap`）。
- **命中投递**：写进对应会话的 `recent`（`delivered_at=0`），按会话聚合后各起一轮唤醒。
  30 个会话一分钟内只有 1 次请求；安静分钟流返回 0 条，直接结束。
- **唤醒前补一次上下文**：流结果没有 `reply_to`，对要唤醒的会话做一次最新 10 条只读，把引用
  原文与媒体键贴回本批（取不到不阻断）。这是每个**唤醒**一次，不是每跳一次。
- **自 @ 指令**：本流里同样能看见（`sender=本人` + `mentions` 含本人），`cmd` 分类不变；
  未值守会话里的启动指令仍由现有 `maybeCommandScan`（1 次/分钟、只查本人 @ 本人）负责，
  不把未值守会话的正文拉进来。

### 2.2 只有要唤醒时才读一次会话

搜索结果不带 `reply_to`，也没有周围上下文。所以：

- 某个会话有未投递命中 → `turns.wake` 之前对该会话做**一次**现有 `fetchThread`（最新 10 条，
  只读），补引用原文、邻近上下文与媒体键；读失败不影响唤醒，载荷按 skill 说明「上下文在线拉」。
- 面板点开会话、手动刷新、首次加入值守的基线：仍走现有按需读。
- 代价：每唤醒一次多 1 次读；唤醒远少于轮询，峰值也不在一分钟内叠加。

### 2.3 慢车道：对账 + 发现（兜底，不承担触发）

- **每 10 分钟发现**：会话列表刷新不变。
- **对账**：每 10 分钟对每个值守会话做一次**区间完整读**（`[poll_since, now]`，飞书
  `--page-all` 取 `meta.pagination.complete`，每轮最多 30 个，按 `verified_at` 轮转）：
  流漏掉的消息在这里被补上（走同一套 `delivered_at` 投递），并记 `runtime.stream.missed`。
  反过来说：流与对账都读过才算「读全」。
- 均摊 ≈ 3 次/分钟；量级与原来的慢车道相同（原来也是每 10 分钟拉一轮全部候选）。

### 2.4 投递：待投集合 + `delivered_at`

- 消息进 `recent` 时带 `delivered_at=0`；**批次 = `recent` 里 `state ∈ {new, opened}` 且
  `delivered_at=0` 的命中类**（`dm`/`mention`/`service`/`cmd`；`all` 模式加 `fyi`），
  单轮上限 30 条。
- 投递成功（消息写进 DSH 会话、拿到 promptId）才写标记；失败不写，下一轮自然重试。
  `wake.failed` 特判、`last_wake_epoch`、`mention_sent` 三个去重机制一并退场。
- `recent` 只淘汰已投递且已处理的行；未投递的命中保住（总量硬上限 50，超出记 gap）。
- **`seen` 环（每会话 50 个 `msg_id`）**：流与对账都会重读重叠区间，靠它保证「同一条消息
  即使已从 `recent` 淘汰也不会被再投一次」；`delivered_at` 负责「给过没给过」，`seen` 负责
  「见过没见过」，两件事分开。
- **本人发言不再吞没看过的 @**：`process()` 的 inline `you-replied` 分支去掉，
  `markEarlierReplied` 只扫 `delivered_at > 0` 的行。

### 2.5 缺口必须可见

- `gap = { at, from, to, source }`（source 当前只有 `backlog`：停机太久、只回看 2 小时）。
  平台不返回被截断的条数，所以不猜数量，只说「还有没读到的」。
- 载荷：`gap.at > max(last_turn.at, session_bound_at)` 时带一句（每轮最多一次）：
  `本群刚刷屏，窗口外还有消息没读到；@ 已单独扫，其余按 skill 在线拉。`
  与现有「另有 N 条没点你名」同一位置，二者取一，净 +0 行。
- 面板：「值守节奏」显示流健康度（上轮读 / 命中 / 未命中 / 截断 / 失败）与最近缺口时间。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 逐会话区间读（上一版） | 正确，但负载仍是 O(会话数)：30 次/分钟、每次固定返回窗口内全部消息；账号级流只要 1 次 |
| 先查「哪些会话有未读」再拉（feed / chat-list 探针） | 把触发绑到人的已读状态；且多一次探针请求，省下的只是安静会话 |
| 只上 @ 兜底搜索，不改读取 | @ 能到，但私聊来信与非 @ 上下文仍静默缺段，缺口无法记账 |
| 只改读取，不上兜底 | 页数上限、索引延迟、停机补读三个口子下 @ 没有保证 |
| 把命令扫描也并进这条流 | 流按 `--chat-id` 收窄到值守会话；并进来就必须读未值守会话的正文，越界。单独留 1 次/分钟的窄搜索 |
| 事件订阅 | 看不到 user↔user 私聊；要 bot 进群 |
| 提高 `per_chat_limit` / 缩短轮询 | 只挪阈值，负载还涨；不解决「窗口就是全部」的错误前提 |

## 实施步骤

1. `lib/im.js`：`searchMessages({chatIds, start, end, pageLimit})`（空 query 流，读
   `has_more`/`total`）；`fetchSince(chatId, {since, until, maxPages})`（飞书取
   `meta.pagination.complete`，企微取 `has_more`，钉钉显式 `complete:unknown`）。
2. `lib/state.js`：`stream_since` / `poll_since` / `verified_at` / `gap` / `seen` /
   `delivered_at` 归一化；`pendingUndelivered(chat)`、`markDelivered(chat, ids)`、
   `markSeen(chat, ids)`；删 `last_wake_epoch`。
3. `lib/poller.js`：`fastCycle` 换成流；`maybeWake` 用待投集合；唤醒前按需读一次上下文；
   `cycle` 加对账轮转；流失败降级到区间读；`gap` 记账。
4. `lib/prompt.js` + `lib/turns.js`：缺口行；投递标记在载荷写进会话后落。
5. 面板流健康度 + 重建 `client.js`；契约 02、`docs/architecture/02-data.md §拉取节奏`、
   `references/feishu.md`（账号流不可用时的降级）、`CHANGELOG.md` 未发布小节。

## 风险与回滚

- **风险：流依赖搜索索引**。实测索引新鲜（流比上一轮拉取还新 60 秒），且慢车道每 10 分钟做
  区间对账兜底；漏掉的消息最迟 10 分钟被补投，并记 `stream_missed`。
- **风险：空 query 是「无过滤」而不是「搜空」**。今天实测可用；若上游收紧，`searchMessages`
  首次失败即降级到区间读（2.3），并把原因写进体检页，不静默。
- **风险：窗口内 >200 条**（只可能停机补读）→ `has_more` + @ 过滤搜索兜 @，其余记 gap。
- **风险：请求集中在整分钟**。流与命令扫描各 1 次、对账 3 次，量级已低于现状；若需进一步
  平滑，把对账改为每 tick 1 个会话（更慢但更平），不改协议。
- **回滚**：撤 commit 即可。新增字段对旧代码是未知字段，旧代码忽略；不需要迁移脚本，不需要
  清 `state.json`。
