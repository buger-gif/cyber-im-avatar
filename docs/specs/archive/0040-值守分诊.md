## 背景

现在的插件是**开关驱动**：用户自己在面板上搜群、点「加入值守」、选「只盯 @我 / 全部消息」。
Agent 只在会话已经进入值守之后才第一次看到它。这带来三个事实：

1. **新群会被发现，但不会被看见。** 慢车道每 `poll.interval_min`（默认 10 分钟）刷一次会话列表，
   `ensureChat()` 会把新群写进 `state.json`，但 `watching=false`、`timer=-1`；`candidates()`
   只选 `timer=1` 的群（`docs/architecture/02-data.md §拉取节奏`）。于是新群在面板里可能连一张卡
   都没有，更不会有 turn。
2. **没在盯的群，@ 也看不见。** 插件是纯拉取（`lark-cli` / `wecom-cli` / `dws`），没有平台推送；
   群不在候选里就不会拉，别人拉你进群后 @ 你也不会触发任何东西。要实时只能另起
   `lark-cli event consume` 之类的长进程，这不是本插件现在的形态。
3. **判断没有发生。** 群名、最近消息、@ 你的人、这个人的档案、你过去对哪些群开过值守——
   这些判断材料在发现/探针之后都拿得到，但现在没有任何一处让 agent 用它们做决定。用户只能
   自己扫一眼群名，凭感觉点开关。
4. **漏网的 @ 只有用户自己会发现。** 没在盯的群不会拉，别人 @ 你之后插件看不见；用户要求
   **隔一段时间清查一次 @ 我的消息**，把新群里漏掉的 @ 捞出来，必要时触发新值班。
   清查只扫**启动基线之后的新群**，存量群完全不考虑；只看最近 24 小时，没 @ 不跑模型。

用户要的是更 AI native 的形态：**被拉进新群，或新群里有人 @ 你之后，分身自己评估这个群值不值得盯，
再决定要不要进入监听值守。** 插件负责把「发生了什么」搬给 agent，agent 负责判断；
执行仍然由插件确定性完成（`AGENTS.md §设计铁律` 第 8 条）。

## 目标与非目标

- 目标：新群被发现（或探针发现有人 @ 你）时，插件生成一张**值守候选**，交给一个常驻的
  「值守台」agent 轮次判断；agent 只能给出 `watch` / `trial` / `ignore` 三种结构化决策，
  插件校验后执行。判断理由落 `state.json`，面板可见、可被用户推翻。
- 目标：判断结果不确定时可用**可选试用**（`trial`，需 `trial_hours>0`）：先按 `mention`
  盯一段时间，到期由同一个值守台复核一次，再决定转正或不盯；不允许无限试用。默认
  `trial_hours=0`，即严格两段式（新建判一次，之后只在 @ 时判第二次）。
- 目标：**分诊创建/开启的新群一律 `wake_mode="mention"`**；决策文件没有 `mode` 选项，
  `all` 不进入分诊。要全量只能由用户事后在现有三态控件里手动改，不属于分诊路径。
- 目标：**定期 @ 清查**——每 `duty.sweep_min` 扫**基线之后、未值守的新群**，发现新的个人 @
  就生成一个 `trigger=sweep` 的分诊事件，走同一套 watch/trial/ignore；**存量群完全不扫**，
  不做 top N 抽样；不下载媒体、没 @ 不跑模型。已在值班的新群跳过，由正常轮询处理。
- 目标：分诊轮**不向群里发消息**（靠值守台 prompt 与群接手轮的 `SKILL.md` 约束；插件不拦截
  agent 的工具调用，与现有「指令默认只在本地处理」同一层保证）；决定值守后另起一场
  「接手轮」，由 agent 按 `SKILL.md` 判断要不要回那条 @。判断与对外发言分开。
- 目标：成本有界——每个新群正常一次探针（10 条消息、不下载媒体）与一次值守台 turn，
  失败最多重试一次；自动分诊有每日配额和值守群上限；没被决定的群不会进入轮询。
- 目标：**不把判断混进常规工作，也不让判断会话膨胀**——值守台是独立私有工作区里的**一个**
  会话，不为每个群建会话；按闲置 / `duty.session_max_turns` 轮换，旧会话留在 DSH 历史；
  `ignore` / `failed` 记录按 `duty.record_keep_days` 清理。群会话仍在原工作区，沿用现有
  生命周期。
- 非目标：不做实时拉群事件。发现仍走 10 分钟慢车道，最坏晚 10 分钟；不把 `lark-cli event`
  搬进插件。
- 非目标：不回溯分诊存量群。升级后只分诊**基线之后新发现**的群；存量未值守群由用户在面板
  手动点「让分身判断」。
- 非目标：不自动盯所有未值守群，不改「群默认不拉」的成本模型，不改 `candidates()` 的口径，
  不改快车道 60 秒节奏。
- 非目标：**不做存量群 / 全量审计**。清查只扫启动基线之后的新群，只看最近
  `sweep_lookback_hours`（默认 24h）内的个人 @；存量群不读、不分诊，也不扫私聊。
  平台判不了个人 @（企微）不扫。
- 非目标：不处理私聊、频道/公告号；插件只有 `p2p` / `group` 两种 kind。
- 非目标：不在插件里写关键词/白名单/规则引擎；判断口径只在值守台 prompt 与用户自己的
  `policy.md` 里。插件不解析 agent 的自然语言回复，只读结构化决策文件。
- 非目标：不新增面板页签、不新增端口、不新增运行时依赖。

## 方案

### 1. 总览：事件 → 探针 → 值守台 → 决策文件 → 执行

```text
慢车道 refreshChatlist（10 分钟）
  └─ 新群（基线之后）→ duty.state=queued（trigger=added）
       └─ 探针：拉 10 条，分类，消费水位，不唤醒、不下载媒体
            └─ 值守台 turn（全局一个 desk session）：
                 事实 + 最近消息 + @ 我的人 + 人物档案路径 + 当前值守名单 +
                 配额 + 值守方针 → agent 判断
                    └─ 写 duty/decisions/<event_id>.json
                         └─ 插件校验 → 应用
                              ├─ watch：watching=1, timer=1, wake_mode=mention；起接手轮
                              ├─ trial：同上 + review_at；到期复核 → watch / ignore
                              └─ ignore：watching=0, timer=-1；待回标 ignored

定期 @ 清查（sweep_min，默认 10 分钟；只扫基线之后的新群）
  └─ 新的个人 @ → duty.state=queued（trigger=sweep）
       └─ 同一套探针/值守台/决策；没有个人 @ 不跑模型、不下媒体
```

三个角色分工：

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 插件（`poller` / `duty`） | 发现、基线、**定期 @ 清查**、探针、排队、配额、校验、执行、trial 到期、面板数据 | 判断群重不重要、判断该不该回、写理由 |
| 值守台 agent（desk session） | 读事实与方针，判断 `watch` / `trial` / `ignore`，写决策文件 | 给群发消息、拉更多历史、改 `state.json` |
| 守护会话 agent（群自己的 session） | 决定值守后的接手轮：看上下文、回不回、怎么写记忆 | 决定要不要值守 |

### 2. 发现与基线

`refreshChatlist()` 每轮遍历会话列表时，在 `ensureChat()` 之前记 `existed`。只有同时满足
下列条件才入队：

- `kind === "group"`、平台在 `config.platforms` 里、未 `blocked`；
- 不是 `watching`；
- `config.duty.enabled !== false`；
- **已经建过基线**（`desk.baseline_at > 0`）；
- `!existed`，或 `chat.added_at > desk.baseline_at && chat.duty.state === "none"`（补漏）。

`desk.baseline_at` 是**第一次成功刷完会话列表**的时刻：至少一个平台 `listChats` 成功返回后，
在处理完该轮所有群之后写入。基线这一轮只登记、不入队，避免首次安装把最近 20 个群一次
分诊；之后新出现的群才入队。基线不因 `duty.enabled` 关闭而重置——用户之后打开自动分诊，
也不会突然把存量群全部分诊。

入队只做一件事：写 `chats[].duty`：

```text
state=queued, trigger=added, event_id=d-<12 hex>, event_at=now,
triaged_at=0, decided_at=0, by="", reason="", confidence=0,
review_at=0, attempts=0, error="", sweep_epoch=<保留原值>
```

不复制群消息、不建会话、不拉取。一个群在 `queued` / `triaging` / `watch` / `trial` 期间不会
重复入队；`failed` / `ignore` 可由面板「让分身判断」用 `force` 重排，或由 sweep 在新的个人 @
时重新排队（见 §3.1）。

`sweep` 事件**不走这条基线条件**：个人 @ 是真实事件，见 §3.1。

发现是**尽力而为**：`poll.dm_recent`（默认 20，飞书夹到 100）之外的群看不到；平台不返回
群、或 `poll.refresh_chatlist=false` 时没有自动分诊。这些都不假装支持；sweep 只覆盖
基线之后的新群 + 24h，存量群不扫。

### 3. 探针：一次、只读正文、消费水位

入队后，`maybeTriage()` 在启动值守台 turn 之前做一次探针：

- 直接调 `im.adapter(platform).fetchMessages(chat_id, {limit: 10})`，**不经过 `candidates()`**，
  不下载媒体，不写 turn 日志正文；
- 同时查**群成员数**（Feishu `+chat-members-list --member-types user --page-all`，只数
  `users[]`；DingTalk/WeCom 没有成员列表 → 0=未知），写 `duty.member_count`；查询失败 /
  `truncations[]` 非空也写 0。成员数只用于 §3.2 的自动开监听硬门，不影响消息探针；
- 用现有的 `process(chat, messages, {baseline, platform, advance: true})` 分类并**消费水位**：
  新群 `baseline=true` 时历史消息记 `ignored`（正文按既有规则清空），非基线时 @ 消息记
  `new`、其余按关注程度规则记；随后 `recent` 与水位一起落盘；
- 把**原始消息**（未清正文）单独返回给这一次分诊 prompt，最多 10 条；它们只进这一次
  DSH turn，不另存、不进日志、不进 `/api/duty`；
- 探针写 `chat.last_sync`（确实同步过）；复核探针不写 `last_sync`，避免影响快车道冷却；
- 探针发现任何非本人的 `isMention()` 命中时，把 `trigger` 从 `added` 升级为 `mentioned`；
  `manual` / `review` 不降级；
- 失败时写 `duty.error`、`attempts += 1`，下一 tick 重试；`attempts >= 2` 记 `failed`。

**为什么探针要消费水位**：不消费的话，决定值守后的下一轮轮询会把同一批消息再当新消息唤醒一次，
同一段上下文跑两遍 turn；接手轮已经拿到探针原文，不需要再投递。它和「点开只读」不同：
点开是用户在看、不想打断自动通道；分诊是一次性消费，消费完就交给判断。

**消费的代价**：如果最终 `ignore` 或分诊失败，探针已经看过的 @ 不会补回待回；这是有意的
（不替用户把旧消息重新变成未读）。面板仍然可以在线看线程，用户手动加入后可以自己回，
或让 agent 从线程里取上下文；插件不偷偷回滚水位。

**试用复核的探针**不消费水位：群此时已经在值守，正常快车道会继续拉；复核只需要一份
最新上下文，用 `fetchMessages()` 原始消息（不 `process`、不推进水位），避免影响正常唤醒。

平台限制照实写进 prompt：

- **自动发现依赖会话列表**：飞书 `+chat-list`、钉钉 `+recent-conversations` 有列表；企微
  adapter 目前没有 `cmd_chats`，`listChats()` 返回「不提供会话枚举」——企微不会自动发现新群，
  也不假装支持。手动分诊仍要求该会话已经在 `state.json` 里（用户先通过面板/搜索登记）。
- 企微 `canMention=false`（没有结构化 mentions，也拿不到本人显示名）——分诊不能建
  `mention` 值守，只能 `ignore`；分诊不允许用 `all` 兜底。
- 谁拉你进群通常只在系统消息里；当前 `im.js` 把 `system` 归一成 `[系统消息]`，所以 prompt
  通常拿不到邀请人。agent 只能据群名、@ 你的人与成员资料推断，推断不出就写「未知」，
  不猜。

### 3.1 定期 @ 清查（sweep）

**判断只发生在两类事件**：

1. **新建 / 首次发现时判一次**（`trigger=added`；探针发现 @ 时升级为 `mentioned`，仍算第一次）：
   决定 `watch` / `trial` / `ignore`；
2. 之后每次 sweep 发现**新的个人 @** 时再判一次（`trigger=sweep`）；同一条 @ 只判一次，
   新的 @ 才算新信号。

没有个人 @ 的群在第一次判断后不再跑模型；sweep 不会因为没 @ 起 turn。已经在值班的群，
@ 直接进群会话，不再做「要不要值班」的第二次判断。`trial_hours=0`（默认）时严格两段式；
如果显式打开试用（`>0`），agent 可以选 `trial`，到期复核一次——这是可选的试用生命周期，
不是对每个群的定时重判。

**为什么**：新群发现只在发现时看一次；一个**新群**当时被 `ignore` / 没来得及看，之后有人
@ 你，正常轮询不会拉（未值守）。sweep 是兜底：**只扫启动基线之后的新群**，找新的个人 @；
**存量群完全不碰、不读、不分诊**。

**范围**：

- 只处理 `chat.added_at > desk.baseline_at` 的新群；`added_at <= desk.baseline_at` 的存量群
  直接排除，不进 sweep、不发请求、不读消息。用户明确要求「已有的群完全不用考虑」。
- 只处理 `kind=group`、平台启用、`mentionable=true`、未 `blocked`、未 `watching` 的新群；
  `queued` / `triaging` 跳过（已有事件）；`watch` / `trial` / `reviewing` 跳过（正常轮询）。
- **Feishu 直接拉 @我 的消息，不逐群扫**：每轮发一条
  `lark-cli im +messages-search --is-at-me --chat-type group --start <lookback> --end <now>
  --page-all --no-reactions`。结果含 `chat_id` / `chat_name` / `sender` / `content` /
  `mentions` / `create_time`；按 `chat_id` 映射到新群，过滤个人 @，命中才生成事件。
  **实测 `--is-at-me` 也会返回 @all / @everyone**，必须再用 `isMention()` 过滤；不能把
  @all 当个人 @。不额外逐群拉 10 条；只有命中的候选在分诊前拉一次上下文 + 成员数。
- **DingTalk 没有 @我 搜索**：退回逐新群 `chat +chat-messages --limit 10`，只扫新群，
  不扫存量；成员数取不到（见 §3.2）。
- **WeCom 没有 mentions / 会话枚举**：不扫，只能手动。
- 每 `duty.sweep_min`（默认 10，0 = 关；>0 时最小 10）一次；Feishu 搜索窗口固定为最近
  `duty.sweep_lookback_hours`（默认 24h），不是「上次到现在」，这样晚发现的新群也能在下
  一轮被捞到；`duty.sweep_epoch` 负责去重。
- 不下载媒体、不写正文日志；只认**个人 @**（`isMention` 命中的非本人消息）；
  `@所有人` / `@全体` 不算。每个命中的新群一个事件；`max_per_day` 配额照旧。

**触发**：

- 新群有新的个人 @（`ts_epoch > duty.sweep_epoch` 且在 lookback 内）→ 写
  `duty.state=queued`、`trigger=sweep`、新 `event_id`/`event_at`；`reason` 留空等 agent。
- 这是**新事件**，即使这个新群之前是 `ignore` / `failed` 也重新排队：新的 @ 是新的信号。
  agent 仍按同一套 rubric 判断，可能再次 `ignore`；`sweep_epoch` 保证同一条 @ 不反复触发。
- 新群如果是 `none`（还没分诊过）也可以触发；但仍要满足 `added_at > baseline_at`，
  存量 `none` 群不在 sweep 范围。
- 命中的原文先放内存，随事件交给分诊；进程重启则 `maybeTriage` 重新探针（会再拉一次
  10 条上下文，仍不下载媒体）。
- sweep 的读 **不写** `last_sync`、不推进正常水位、不更新 `recent`；只更新
  `duty.sweep_epoch` 和事件。新群之后被值守时，正常轮询仍能按自己的水位看到这些消息。

**去重水位 `duty.sweep_epoch`**：

- sweep 处理完把 `sweep_epoch` 推到本次看到的最新 `ts_epoch`（即使没 @），下次只看更新的。
- 分诊探针（新群 / sweep / 手动）也把 `sweep_epoch` 推到探针看到的最新；`watch` / `trial` /
  `ignore` 应用时推到当前 `last_epoch`，避免把已经在值守/试用期间处理过的 @ 再当成新的
  清查事件。
- 用户手动 watch/off 同样推进；记录清理不把 `sweep_epoch` 回退到 0。
- sweep 探针本身只读；首次开监听应用 `watch`/`trial` 时，用本次探针消息的最新时间推进
  正常水位。接手轮已经拿到这批消息，避免下一轮快车道把同一批 @ 再唤醒一次。

**代价**：

- Feishu：每 10 分钟 1 条 `+messages-search`（`--page-all` 最多 20 页），不再按群数拉取；
  只有命中的候选才多一次上下文探针 + 成员数查询。没有个人 @ 时 0 模型。
- DingTalk：每个未值守新群 144 次/天（逐群回退）；`sweep_min=0` 可关。
- 模型：sweep 本身 0 token；只有发现个人 @ 并排队后才走一次分诊 turn（和 discovery 事件
  同一套成本）。
- 隐私：Feishu 只把搜索结果里命中新群的 @ 交给分诊；DingTalk 只读新群；存量群不读；
  不下载媒体、不写日志；`sweep_min=0` 可关。

**限制**：

- 只扫基线之后、已经被发现的新群；新群如果超出 `poll.dm_recent` 或
  `refresh_chatlist=false` 没进 state，Feishu 搜索结果会先被忽略，等下一轮发现后再命中；
  DingTalk 逐群回退就看不到。存量群永远不扫。
- Feishu 的 `--is-at-me` 包含 @all，必须过滤；搜索结果有页上限（`--page-all` 默认 20 页），
  极端多 @ 时下一轮继续。
- 只看最近 24h；更早的 @ 不自动补，面板可手动「让分身判断」。
- 企微没有会话枚举、也判不了 @，不扫。
- 不是全量审计，不保证所有新群 @ 都被捞到；它是低成本兜底。

### 3.2 群成员上限：超过 10 人不自动开监听

**为什么**：大群噪声大、@ 多、值守价值低；用户要求**超过 10 个人**的群不自动开监听。
这是自动路径的硬门，手动仍然可以开。

- **只数人**：Feishu `im +chat-members-list --chat-id <oc_...> --member-types user
  --page-all`，取 `users[]` 数量；不要把 bots 算进去。`truncations[]` 非空表示服务端截断，
  人数不可信，按「未知」处理。
- **上限**：`duty.max_group_members` 默认 `10`，范围 0–1000；`0` = 不限。成员数 `> 10`
  → 自动路径只能 `ignore`；插件拒绝 `watch` / `trial`（`error=group_too_large`）。
- **取不到人数**：DingTalk 当前没有成员列表命令、WeCom 没有会话枚举；取不到就按「未知」，
  自动路径只能 `ignore`（`error=member_unknown`），**不猜、不放行**；要值守用手动。
- **检查时机**：新群第一次判断前、sweep 命中的候选分诊前各查一次；结果写
  `chats[].duty.member_count`（0 = 未知）。已经在值班的群后来长到 >10，不自动停
  （用户要求的是「不自动开」，不是自动关）；面板可手动关。
- **手动优先**：用户手动 watch / 改关注程度不受这个上限限制；面板显示「N 人 / 自动上限 10」，
  超限时说明「只能手动开」。
- **硬门**：agent 的 `watch` / `trial` 决策即使写了，插件在 `applyDecision` 也会拒绝；
  `reason` 和面板都能看到 `group_too_large` / `member_unknown`。

### 4. 值守台：全局一个 desk session、私有工作区、独立寿命

判断不放在新群自己的会话里，也不放在用户的项目工作区里，而是放在一个**插件私有的全局值守台**：

- **独立工作区**：cwd 固定 `<state.dir>/duty/`，不是用户的项目/仓库。插件只在这里写
  `policy.md` 与 `decisions/`；不读项目文件、不写用户工作区，也不注册到 DSH 的 workspace
  列表（避免污染工作区选择器）；如果 DSH 侧边栏按 cwd 分组，它自然单独一组。
- **只建一个会话**：`state.data.desk.dsh_session`，第一次分诊懒创建，之后复用。分诊**不为
  每个候选群建会话**；只有决定 `watch` / `trial` 后，群自己的会话才按现有 `Turns.open`
  创建/复用。群会话仍在那个群原来的工作区——值守台只做判断，不接管群工作。
- **目录**（插件创建 0700）：

```text
<state.dir>/duty/                 0700  值守台工作区（独立，不是用户项目）
├── policy.md                     0600  agent 维护的值守方针；插件安装/启动时缺/空才写入初始版本，
│                                       已有内容不覆盖，判断时只给路径
└── decisions/<event_id>.json     0600  一次判断的决策；插件读后删除
```

- **会话寿命**：满足任一条件，就在下一个事件前解绑重开：
  - 闲置超过 `2 × dsh.warm_min`；
  - 插件累计 turn 达到 `duty.session_max_turns`（默认 20，0 = 不限）；
  - cwd 不符（用户改过 / state 搬家）或 DSH 会话丢失。

  解绑时清空 `desk.dsh_session` / `session_turns` / `prompt_session` / `session_bound_at` /
  `last_error`；旧值守台会话留在 DSH 历史，插件不删除（DSH 没有删除接口）；`policy.md` 不丢。
  首轮 preamble 带最近 5 条判断，换会话不丢口径；长期方针仍在 `policy.md`。
- **只统计插件自己的 turn**：用户手动进值守台聊天不计入 `session_max_turns`；闲置重开仍会
  收口。判断是简单重复的动作，不需要一个无限长的会话。
- **不打断**值守台里已经在跑的轮次（用户可能正在跟它说话）。`maybeTriage()` 发现
  `desk` 在飞或 `agent.status === "running"` 就跳过，事件留在 `queued`，下一 tick 再试；
- 一次 tick 最多启动一个值守台 turn；**复核优先于新分诊**，避免试用群无限期挂着；
- 值守台 turn 不写群会话的 `last_turn` / `session_turns` / `wake`，只写 `desk.*`；
  事件日志记 `platform` / `chat_id`（候选群）、`turn_id`、`state`，不记群名与正文；
- 值守台是真正的 DSH 会话，会出现在侧边栏。面板「分身」页给一张「值守台」卡（最近判断、
  会话 id、判断轮 `N / 上限`、去会话）；用户也可以直接进去说「以后这种客户群都盯着」，agent
  按值守台 prompt 的格式更新 `policy.md`。
- **群会话不搬进值守台**：值守群沿用原 workspace 与现有 `2 × dsh.warm_min` 会话寿命；
  `duty.max_groups` 限制同时值守群数，分诊本身不制造每群一个会话。想给某个值守群隔离
  工作区，用现有 per-chat workspace 绑定；插件不把群工作搬进值守台。
- **已拍板（2026-11-09）**：选「只隔离判断」——只有分诊/值守台在私有工作区；值守群会话
  仍用原 workspace，不强制搬进独立工作区。理由是群工作要读项目上下文、写群工作本，
  搬走会丢上下文；某个群确实要隔离时用现有 per-chat workspace 绑定。

### 5. 决策文件：唯一的判断出口

值守台 agent 只写一个文件，插件只读这一个文件。路径与内容：

```text
<state.dir>/duty/decisions/<event_id>.json
```

```json
{
  "version": 1,
  "decision_id": "d-1a2b3c4d5e6f",
  "platform": "feishu",
  "chat_id": "oc_example",
  "action": "watch",
  "reason": "项目群，同事 @ 你排期；先只盯 @我",
  "confidence": 0.82,
  "review_at": 0
}
```

| 字段 | 必填 | 校验 |
| --- | --- | --- |
| `version` | 否 | 缺省 1；不是 1 拒绝 |
| `decision_id` | 是 | 必须等于本次事件的 `event_id` |
| `platform` / `chat_id` | 是 | 必须与当前候选一致，不能借文件改别的会话 |
| `action` | 是 | `watch` / `trial` / `ignore`；复核只允许 `watch` / `ignore`；`trial_hours=0` 时 `trial` 拒绝（`trial_disabled`） |
| `reason` | 是 | 单行，1–160 字；插件去控制字符，不写聊天原文/手机号/邮箱 |
| `confidence` | 否 | 0–1，缺省 0.5；面板不展示数值，只留状态 |
| `review_at` | 否 | `trial` 可给 epoch 秒，夹到 `[now+1h, now+trial_hours]`；缺省 `now+trial_hours` |

校验规则：

- 只读普通文件（`lstat` 拒绝符号链接），上限 16 KiB；JSON 解析失败 → `failed`；
- 文件里的 `platform`/`chat_id` 与当前事件不一致 → 拒绝，不作用于别的会话；
- `watch` 时群已被删、已屏蔽、平台已停用 → 丢弃，记 `error`；
- **群成员上限**：只在「从未值守变为 watch/trial」时检查（复核 `watch` / trial 转正不算新开）。
  `duty.max_group_members>0` 时，`member_count > 上限` → 拒绝 `watch`/`trial`
  （`error=group_too_large`）；`member_count=0`（未知）→ 拒绝（`error=member_unknown`）。
  `ignore` 永远允许。用户手动 `/api/watch` / `/api/chat/mode` 不走这个门，可强制开。
- 用户在同一事件里已经手动改过关注程度（`duty.by === "user"` 且
  `duty.decided_at >= duty.event_at`）→ 作废 agent 决策；
- 应用成功后尽力删除文件；删除失败不影响状态，残留文件由每日清理（7 天）收走；
- **启动前先看文件**：每次启动分诊/复核 turn 前，先按当前 `event_id` 找决策文件；有且合法
  就直接应用、不再跑 turn。覆盖「决策已写、回调丢失/进程重启」的窗口；
- 插件**不解析** agent 的最终文本、不读 assistant 消息、不从正文里抽 JSON。

### 6. 应用：三种动作

`applyDuty(chat, decision, { by })` 是**决策执行**的唯一入口：agent 决策文件走它；
用户手动操作保留现有 `/api/chat/mode` / `/api/watch` / `/api/unwatch` / `/api/chat/block`
路径，但通过 `recordUserDecision()` 写同一份 duty 记录，状态与理由不会两套。

| 动作 | 写入 | 后续 |
| --- | --- | --- |
| `watch` | `watching=1`、`timer=1`、`wake_mode="mention"`、`target=1`；`duty.state=watch`、`by`、`decided_at`、`reason`、`confidence`、`review_at=0` | `profiles.ensureMemory()`；首次从「不盯」变值守时起**接手轮** |
| `trial` | 同上，`duty.state=trial`、`review_at` | 同上；到期进复核 |
| `ignore` | `watching=0`、`timer=-1`（`target` 不动）；`duty.state=ignore`、`by`、`decided_at`、`reason`、`review_at=0` | 取消在飞 turn；把该会话 `new/opened` 的待回标 `ignored` 并清正文；不起 turn |

补充约束：

- **接手轮**（`Turns.open(chat, {reason:"duty", context: probeMessages})`）：载荷比普通开场多
  一段「分诊判断 + 理由 + 探针看到的消息」，明确这是决定值守后的第一轮，有该回的就按
  `SKILL.md` 回，没有就不发；探针消息不因超过 30 分钟被丢掉，也不再变回待回。接手轮失败
  不回滚 `watching`，只写 `duty.error`，下一条消息照常唤醒，面板可「现在处理」。
- **用户优先**：面板 `/api/chat/mode`、`/api/watch`、`/api/unwatch`、`/api/chat/block`
  都调用同一个 `recordUserDecision()`；有 duty 记录就写 `by=user`、`decided_at=now`、
  `reason="你在面板设置"`，并取消 `review_at`。用户操作后，在飞分诊的决策文件作废。
- **分诊不产生 `all`**：`applyDuty` 永远写 `wake_mode="mention"`；用户手动把某个群改成
  「全部消息」仍走现有三态控件，属于用户动作，不由分诊产生。
- **上限**：`duty.max_groups` 只在「从未值守变为值守」时检查；试用转正不占新增名额。
  达到上限时 agent 的 `watch`/`trial` 不执行，记 `state=failed`、`error=watch_cap`、
  `by=agent`，面板显示「判断为值守，但已达上限，可手动开启」；用户手动开启不受限。
- **屏蔽/删除**：应用前重新从 `state` 取 chat，确认还在、未屏蔽、kind 还是 group；否则丢弃。
- **幂等**：同一 `event_id` 已经应用过（`duty.decided_at > 0` 且 `event_id` 相同）就跳过，
  避免重启后重复起接手轮。

### 7. 可选试用与复核

- `config.duty.trial_hours` 默认 0，范围 0–168；`0` = 关闭试用（默认，严格两段式），
  agent 只能 `watch` / `ignore`；`>0` 才允许 `trial`，到期复核一次。校验层在
  `trial_hours=0` 时拒绝 `trial`（`error=trial_disabled`），不写成永久值守。
- `trial` 应用后 `review_at` 写入；`maybeReview()` 在 `maybeTriage()` 之前跑，一次 tick
  最多一个值守台 turn。复核是**新事件**：生成新的 `event_id`/`event_at`；`attempts` 保留，
  最多 2 次，仍未完成就自动 `ignore`（`reason=试用复核两次失败`）；
  `triaged_at` 不动。
- 到期复核载荷：试用开始/到期时间、这期间群里的最近 10 条原始消息（只读探针）、
  `session_turns`、待回数、最近 turn 结果、当前 `wake_mode`；要求只能 `watch` 或 `ignore`，
  **不能再 trial**，避免无限续期。复核不写 `triaged_at`，不占每日分诊配额。
- 复核 `watch` 只取消 `review_at`/把 `state` 改成 `watch`，**不再起接手轮**（群已经在值守，
  正常消息会唤醒）；`ignore` 与上表相同。
- 超时：`review_at + 60 分钟` 仍没有合法决策 → `state=ignore`、`by=system`、
  `reason="试用期满未复核"`，不无限挂着。复核决策非法/缺失不立刻关闭：退回 `trial`、
  记 `error`，下一 tick 重试，直到宽限窗口用完。
- `duty.enabled=false` 时：不自动复核；所有 `trial` 到 `review_at` 直接自动 `ignore`
  （`by=system`），避免关掉开关后试用变永久值守。
- 用户手动转正 / 不盯 → 立即取消 `review_at`，不再复核。
- 复核 turn 不计入 `duty.max_per_day` 配额（它不新增值守群）；但它仍然占一次值守台 turn，
  所以可能让新群分诊晚一个 tick。

### 8. 状态、配置与配额

`chats[].duty`（追加在 `normalizeChat()` 末尾，默认全空；老 state 不改变行为）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `state` | string | `"none"` | `none` / `queued` / `triaging` / `watch` / `trial` / `reviewing` / `ignore` / `failed` |
| `trigger` | string | `""` | `added` / `mentioned` / `manual` / `review` / `sweep` |
| `event_id` | string | `""` | 本次事件的稳定 ID，也是决策文件名；重试不变 |
| `event_at` | number | `0` | 入队时刻（epoch 秒） |
| `triaged_at` | number | `0` | 上一次启动**新群分诊** turn 的时刻；复核不写它；配额按它统计 |
| `decided_at` | number | `0` | 决策应用时刻；0 = 未决定 |
| `by` | string | `""` | `agent` / `user` / `system` |
| `reason` | string | `""` | 判断理由，单行 ≤160 字 |
| `confidence` | number | `0` | 0–1；不展示数值 |
| `review_at` | number | `0` | trial 复核时刻；其它状态为 0 |
| `attempts` | number | `0` | 分诊启动次数；自动重试上限 2 |
| `error` | string | `""` | 最近失败原因（`no_decision` / `invalid` / `watch_cap` / `stale` …） |
| `sweep_epoch` | number | `0` | @ 清查水位：已看过的消息时间；只触发更新的个人 @；清理记录时保留 |
| `member_count` | number | `0` | 群成员数（只数人）；0 = 未知；超过 `duty.max_group_members` 时自动路径只能 ignore |

顶层 `desk`（追加在 `defaultState()` 末尾，默认空对象；不升 `STATE_VERSION`）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `workspace` | string | `""` | 固定为 `<state.dir>/duty`；空=还没建 |
| `dsh_session` | string | `""` | 值守台 DSH 会话 |
| `session_bound_at` | number | `0` | 会话绑定时刻 |
| `session_turns` | number | `0` | 值守台累计 turn 数 |
| `prompt_session` | string | `""` | 已消费过完整分诊 preamble 的会话 |
| `last_turn` | object | `{ok:null,reason:"",at:0}` | 最近值守台 turn |
| `last_error` | string | `""` | 最近值守台错误 |
| `baseline_at` | number | `0` | 首次成功刷完会话列表的时刻；0=还没建基线 |
| `last_sweep_at` | number | `0` | 上一次 @ 清查开始的时刻；0=还没清查过 |

`State.load()` 对存量数据只补默认值：`duty.state="none"`、`desk` 全空。启动时把
`triaging` 还原成 `queued`（进程重启，turn 已不在），把 `reviewing` 还原成 `trial`
（复核没跑完，`review_at` 还在）；`attempts` 不重置，重试上限照旧。不升 version。

配置（追加到 `DEFAULT_CONFIG` 与 `docs/specs/contracts/03-config.md`）：

| 键 | 默认 | 范围 | 说明 |
| --- | --- | --- | --- |
| `duty.enabled` | `true` | true / false | 自动分诊总开关；关闭后仍可手动「让分身判断」 |
| `duty.trial_hours` | `0` | 0–168 | 试用时长；0 = 关闭（默认，严格两段式），只能 watch / ignore；>0 才可 trial |
| `duty.max_groups` | `20` | 0–200 | 自动决策可新增的值守群上限；0 = 不限；手动不受限 |
| `duty.max_per_day` | `20` | 0–200 | 每天自动分诊 turn 上限；0 = 不限；复核与手动不占 |
| `duty.session_max_turns` | `20` | 0–200 | 值守台会话累计插件 turn 上限；达到后下一个事件换新会话；0 = 不限 |
| `duty.record_keep_days` | `30` | 0–365 | `ignore` / `failed` duty 记录保留天数；0 = 永不清；`watch` / `trial` 不清 |
| `duty.sweep_min` | `10` | 0 或 10–1440 | @ 清查间隔（分钟）；0 = 关；扫基线之后的新群 |
| `duty.sweep_lookback_hours` | `24` | 1–168 | 只把最近多少小时内的个人 @ 当作新事件；更早的不自动补 |
| `duty.max_group_members` | `10` | 0–1000 | 自动开监听的群成员上限（只数人）；超过或未知只能 ignore；0 = 不限；手动不受限 |

配额与上限都是**派生**，不另存计数器：

- `quota_used` = `triaged_at` 落在本机自然日的会话数（复核不写 `triaged_at`，所以不占配额）；
- `watch_groups` = `watching && kind === "group"` 的会话数（含 trial）；
- 配额用完时，`queued` 事件**不丢**，等次日自然日再跑；超过 24 小时仍没跑到的事件记
  `failed` / `error=stale`，面板可手动重排。
- `duty.enabled=false` 只挡自动 `added`/`mentioned`/`sweep`；`manual` 事件仍启动，`review`
  直接自动 `ignore`（不跑 turn）。`sweep_min=0` 只关清查，不影响新群分诊。

#### 会话与记录寿命

判断是简单重复动作，不需要无限长会话；清理分四层，互不影响：

- **值守台会话**：闲置 `2 × dsh.warm_min`，或插件累计 turn 达到
  `duty.session_max_turns`（`>0` 时），在下一个事件前清空 `desk.dsh_session` /
  `session_turns` / `prompt_session` / `session_bound_at` / `last_error`，下次事件懒开新会话。
  旧会话留在 DSH 历史，插件不删（DSH 没有删除接口）；`policy.md` 与最近判断仍在，换会话不丢口径。
- **决策文件**：应用成功即删；未应用的 `decisions/<event_id>.json` 每天清理超过 7 天的
  普通文件（`lstat`，不跟符号链接）；`policy.md` 永不清理，由 agent 自己按记忆整理规则
  压缩，插件不读、不写、不代做。
- **duty 记录**：每天把 `state=ignore|failed` 且 `decided_at` 超过
  `duty.record_keep_days` 的记录清回 `state=none`（除 `sweep_epoch` / `member_count` 外归零）；`watch` / `trial`
  不清；`chats` 行本身不动（发现/删除逻辑不变）。清掉后该群不会自动重排队（`added_at` 已早于
  baseline），需要时手动「让分身判断」。
- **群会话**：沿用现有 `2 × dsh.warm_min` 换会话；`ignore` 只停止轮询并把待回标 ignored，
  **不删 DSH 会话**（没有删除接口），旧会话留在历史；`duty.max_groups` 限制同时值守群数。

### 10. 值守台载荷（不加载完整 skill）

值守台 prompt 由插件 `buildDeskPrompt` 生成，**不注入 `/cyber-im-avatar`**：它只做注意力
判断，不需要 IM 闭环、平台命令或画像规则；群接手轮才加载 skill。首轮带完整职责与决策
schema，后续轮只带事件与决策路径。首轮结构：

```text
（值守台，不是客户消息）
你是值守台，不是群里的替身。只判断，不发消息。
值守台 · 飞书 · 新群
候选：示例项目群
chat_id：oc_example
触发：会话列表发现新群 / 探针发现有人 @ 你 / 定期清查发现有人 @ 你
上次判断：无（首次发现）/ ignore（广告群，不盯）
探针：最近 10 条（只读，未回复；媒体未取回）
- [时间] 张三: ……
- [时间] 李四（@你）: ……
人物档案：
- 李四 · ou_xxx → /.../profiles/people/feishu/ou_xxx.md（读不到就跳过）
当前值守：12 个群 / 上限 20；今日已分诊 4 / 20
群成员：8 人（自动上限 10；超过或未知只能手动）
最近判断：
- 示例客户群 → ignore（广告群）
- 示例项目群 → watch（项目群，@ 你排期）
值守方针：/.../duty/policy.md（插件已补初始版本；存在时读）
若用户在本会话给出长期偏好，按「值得值守 / 先试用 / 不盯 / 硬约束」四段更新它。
你的任务：
1. 判断这个群值不值得值守：watch / trial / ignore。
2. 只写决策文件：/.../duty/decisions/<event_id>.json
   （字段见本次 prompt；没有 mode，新群一律 mention）
3. 不给这个群发消息，不拉更多历史，不运行 listen_cli，不写 state.json。
判断口径：
- 硬门优先（平台判不了 @ / 屏蔽 / 达上限 → ignore）。
- 个人 @ + 工作上下文/具体请求 → `trial` 开时 trial、关时 watch；没有个人 @ → trial 开时
  trial、关时 ignore（等 @）；无工作信号 → ignore。
- @所有人 不算个人 @；只允许 mention，不提供 all。
```

首轮还带**最近 5 条判断**（群名 → `watch` / `ignore` + 理由，按 `decided_at` 倒序，当前
候选除外）；它是换值守台会话时的短期记忆，后续轮不重复。长期方针仍在 `policy.md`。

`trigger=sweep` 时，载荷明确写「这是定期清查发现的 @，可能已经过去几小时」；如果该群之前
有决定（`decided_at>0`），带「上次判断：action / reason / 时间」，第二次判断要说明新 @ 是否
改变结论；判断仍按同一 rubric，不要因为旧就自动忽略，但 `reason` 要写清查看到的证据。
上次判断在事件入队时从内存带过去，重启丢失则按新证据判。`trigger=added` / `mentioned`
仍是新群/探针路径。

首轮末尾给默认判断口径。完整口径只写在 `buildDeskPrompt` 的默认段；prompt 每次只带本次
需要的摘要（默认 `mention`；trial 关时没有 @ 就 ignore 等 @；不上限硬撑），不把整节抄进载荷：

- 工作相关、你被直接 @ 或被点名、用户角色确实相关 → `watch`，默认 `mention`；
- 群名/上下文不清楚、刚被拉进来只有一条 @、可能是临时群 → `trial`，默认 `mention`；
- 大群/公告/营销/纯社交/与用户工作无关、重复已有群、用户方针明确说不盯 → `ignore`；
- 分诊只产生 `mention`；不提供 `all`，新群一律只盯 @我；
- `mentionable=false` 的平台只能 `ignore`（判不了 @，又不许 all 兜底）；
- 已达值守群上限 → `ignore` 并在 `reason` 说明，不越权；
- 理由要具体（「项目群，@ 你排期」），不写「看起来重要」；
- 不确定：trial 开 → trial；trial 关 → 有个人 @ + 工作上下文就 watch，没有 @ 就 ignore
  等 @；不硬猜。

#### 接管判断口径（默认 rubric）

先把「接管」说死：`watch` / `trial` = 开始盯这个群，**只在有人个人 @ 你时才唤醒群会话**；
不等于替你在群里发言，也不等于每条都回。真正的回复仍由接手轮按 skill 判断。

**硬门**（插件/成本边界，agent 不能越过）：

1. 平台判不了个人 @（如企微）→ 只能 `ignore`，不能 watch/trial。
2. 群被屏蔽 / 已删 / 平台停用 → `ignore`。
3. 已达 `duty.max_groups` → agent 只能 `ignore`；插件拒绝 watch/trial（`watch_cap`）。
4. 群成员数 > `duty.max_group_members`（默认 10）或未知 → 只能 `ignore`；插件拒绝
   watch/trial（`group_too_large` / `member_unknown`）。手动可强制开。
5. `duty.enabled=false` 或配额用完 → 不自动判；配额用完排队，手动才判。
6. 用户在同一事件里已手动设置 → 用户优先。

**信号**（agent 按这些判断；理由要点出依据）：

| 信号 | 含义 | 强弱 |
| --- | --- | --- |
| S1 工作上下文 | 群名/成员/消息指向项目、客户、团队、交付、排期、决策；你是参与者/负责人 | 强 |
| S2 个人 @ | 真人 @ 你个人；`@所有人` / `@全体` 不算 | 强 |
| S3 具体请求 | 明确要你做/确认/决定/给东西；不是「在吗」「欢迎」 | 强 |
| S4 认识的人 | @ 你的人是已知同事/客户/老板，或群里有多个你档案里的人 | 中 |
| S5 活跃小群 | 最近 10 条有多个真人、有来有回；不是公告/营销 | 中 |
| S6 用户方针 | `policy.md` 明确说这类群 watch/trial/ignore | 强（覆盖默认） |
| N1 噪声群 | 大群公告/营销/纯社交/临时聚会 | 强负 |
| N2 无工作信号 | 只有「欢迎」「拉你进来」；群名/成员看不出工作 | 强负 |
| N3 重复覆盖 | 同一项目/客户已经在盯 | 中负 |
| N4 临时/一次性 | 临时群、聚餐、活动、一次性讨论 | 中负 |

**决策表**：

| 情况 | 动作 |
| --- | --- |
| 命中硬门 | `ignore`（或排队/不判） |
| S2 + S3 +（S1 或 S4） | `watch` |
| S2 + S1，没有 S3（「在吗」「欢迎」） | `trial` 开 → `trial`；关 → `watch`（只盯 @） |
| 没有 S2 + S1 +（S4 或 S5）（被拉进一个工作群） | `trial` 开 → `trial`；关 → `ignore`（等 @；S6 明确 watch 除外） |
| S2 + S4，但 N1/N4 明显（社交/临时） | `ignore`（除非 S6 说 trial） |
| 没有 S2 + 没有 S1/S4 | `ignore` |
| 证据不足、拿不准 watch/trial | `trial` 开 → `trial`；关 → 有 S2 + 工作上下文 → `watch`，否则 `ignore` |
| 拿不准 trial/ignore，且没有任何工作信号 | `ignore` |
| S6 明确 watch/trial | 按 S6，除非命中硬门 |

信号是判断依据，不是硬性打分；按「硬门 → S2+S3 的具体请求 → 其余」的顺序看。N1/N4 是
负信号，不是绝对硬门：如果 S2+S3 明确指向你（例如大群里老板 @ 你「这个项目你跟一下」），
仍可 watch/trial，理由里写明。

**两条默认口径**：

- 默认判断下，`watch` 至少两个独立信号，其中一个必须是 S2；**没有个人 @ 就不 watch**
  （trial 开时可 trial，关时 `ignore` 等 @）。S6 明确说 watch 时按 S6。
- `trial` 开时，至少一个弱工作信号（S1/S2/S4 之一）；trial 关时，S2 + 工作上下文可以直接
  watch，没有 @ 就 ignore 等 @；完全没有工作信号 → `ignore`，不拿试用赌。

**例子**：

| 场景 | 判断 | 理由 |
| --- | --- | --- |
| 项目群，同事 @「周三前给排期」 | `watch` | S1+S2+S3+S4 |
| 客户群，客户 @「在吗」 | `watch`（trial 关）/ `trial`（开） | S1+S2+S4，缺 S3 |
| 行业交流 500 人，无 @，只有广告 | `ignore` | N1+N2 |
| 公告群，「@所有人 明天停电」 | `ignore` | `@all` 不算 S2；N1 |
| 老板拉进项目群，@「这个项目你跟一下」 | `watch` | S1+S2+S3+S4 |
| 前同事临时群，@「来聚餐」 | `ignore` | S2+S4，但 N1/N4（社交/临时） |
| 群名未知，只有「欢迎」 | `ignore` | N2；若拉你的人是已知同事 → `trial` |
| 企微群 @ 你 | `ignore` | 硬门 1：判不了个人 @ |
| 已盯 20 个群，新项目群 @ 你 | `ignore` | 硬门 3：cap；面板提示手动 |

**判断顺序**：硬门 → 读 `policy.md`（明确规则优先）→ 标 S/N → 套决策表 → 拿不准 trial /
无工作信号 ignore → 写决策文件，`reason` 点出依据（群名/@/谁/具体请求），不写「感觉重要」。

`SKILL.md` **不加**值守台章节：值守台规则只在 `buildDeskPrompt` 与 `policy.md`；群接手轮
仍按现有 `SKILL.md`，不因为分诊改变。这样值守台不用把 8–15k 的完整 skill 再灌一遍，
判断的固定成本降到约 1.5–2.5k 的职责/口径段。

`policy.md` 是 agent 自己的文件（初始版本即四段：值得值守 / 先试用 / 不盯 / 硬约束）。
插件在安装/首次启动、或本地文件缺失/为空时写入初始版本；已有非空内容绝不覆盖，也不解析。
用户在值守台说「以后这种客户群都盯着」时，agent 按 prompt 里的格式更新它；下次分诊自动带上。

接手轮在 `buildOpenPrompt` 里加一段：

```text
值守判断：watch（只盯 @我）
判断理由：项目群，同事 @ 你排期
这是决定值守后的接手轮；下面是分诊时看到的最近消息。
有该回的就按 skill 回，没有需要回的就不要往群里发消息。
```

### 11. 成本、隐私与边界

- 每个新群：1 次 `fetchMessages`（10 条）+ 1 个值守台 turn；决定值守再加 1 个接手轮。
  自动分诊受 `duty.max_per_day` 限制，值守群受 `duty.max_groups` 限制。
- trial 不是免费的（默认关；打开后）：试用群按 `poll.fast_sec`（默认 60 秒）进快车道，
  24 小时约 1440 次拉取；把 `duty.trial_hours` 调小、或让 agent 直接 `ignore`，都能省这笔拉取。
- 探针不下载图片/文件，不把正文写日志；10 条原文只进这一次 DSH turn。它和正常值守一样，
  是本地插件把正文交给用户自己的 DSH agent，不上传第三方、不写 `turns.jsonl`。
- **没在值守的新群 @ 你**由 `sweep` 兜底：每 `duty.sweep_min`（默认 10 分钟）处理
  **基线之后、未值守的新群**；Feishu 只发 1 条 `--is-at-me` 搜索，DingTalk 才逐新群读
  10 条；sweep 本身 0 token，只有发现个人 @ 才走一次分诊。最坏晚一个 sweep 周期；
  `sweep_min=0` 可关。不下载媒体、不写日志，只把命中原文交给这一次分诊；存量群完全不读。
- 分诊轮不对外发言；接手轮才可能按 skill 回复。决定 `ignore` 时不会向群里发任何东西。
- 发现延迟最坏 10 分钟；没在值守的群 @ 最坏晚一个 sweep 周期（默认 10 分钟）。这是拉取
  模型的代价，不是 bug。要更快只能改发现/清查节奏或上平台事件，都不在本次范围。
- 分诊只产生 `mention`；`all` 仍可由用户手动在现有三态控件里选，不由分诊产生。群默认不拉
  （`timer=-1`）不变；只有被决定的群才进 `candidates()`。
- **判断不混进常规工作**：值守台 cwd 固定在 `<state.dir>/duty/`，不注册到用户工作区列表、
  不读项目文件、不写用户仓库；群的工作仍在群原来的 workspace，由群会话处理。
- **判断会话不膨胀**：值守台全局只有一个，不按群建；闲置 `2 × warm_min` 或累计
  `duty.session_max_turns` 轮就换新会话，旧会话留在 DSH 历史（插件不删）。判断记录
  `ignore` / `failed` 按 `duty.record_keep_days` 清理；`watch` / `trial` 保留；决策文件
  应用即删、未应用的 7 天清理。
- 误判可由面板推翻：`watch` 可改「不盯」，`ignore` 可手动「加入值守」或「重新判断」；
  决策理由一直显示。

### 12. 成本模型：什么时候触发、每次花什么

分诊是**事件驱动**，不是定时心跳。没有新群/复核事件时，值守台一次模型调用都不发生；
10 分钟发现、60 秒快车道都不是模型触发频率。

| 事件 | 触发频率 | 模型调用 | CLI |
| --- | --- | --- | --- |
| 新群发现（基线后） | 每个新群一次，最坏晚 10 分钟；受 `max_per_day` 限制 | 1 个分诊 turn | 1 次探针拉 10 条 |
| 试用到期复核 | 每个 trial 一次，约 `trial_hours` 后 | 1 个复核 turn | 1 次只读探针 |
| 决定 watch/trial | 每个被决定的群一次 | 1 个接手轮（群自己的会话） | 0–1 次（按需） |
| 值守群轮询 | 快车道 `fast_sec`（默认 60 秒）/群 | 0；只有消息命中才唤醒群会话 | 1 次/轮 |
| @ 清查（sweep） | Feishu：每 `sweep_min` 1 条 `--is-at-me` 搜索；DingTalk：每个未值守新群 1 次/轮 | 0；只有个人 @ 才 1 个分诊 turn | Feishu 1 次搜索 + 候选探针；DingTalk 1 次/新群 |
| 没有新群 / 没有 @ | — | 0 | sweep 仍按间隔拉，但不跑模型 |

**token 消耗**（粗略，按中文与常见消息长度；实际取决于消息长度、模型与缓存）：

| 部分 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| 分诊 prompt | 1.5–3k | 0.2–0.5k | 10 条短消息 + 群名/@/人物路径/配额；消息很长时到 ~8k |
| 值守台首轮 | +1.5–2.5k | — | 紧凑职责/口径段，**不加载完整 skill**；每个值守台会话一次 |
| 接手轮 | 8–15k | 0.3–1k | 群会话首轮：skill + 工作本/档案 + 最近消息；本来加群值守也有这笔 |
| 复核 turn | 1–3k | 0.2–0.5k | 加上值守台已有上下文 |

> 上表不含 agent 主动读 `policy.md` / 人物档案的内容；读一份约 +0.5–2k，按需。分诊不强制
> 读全部，读不到就跳过。

值守台是同一会话续跑，模型每轮会重读已有上下文；`session_max_turns` 管这个：

- 20 轮：少建会话，但后几轮输入随历史增长；
- 5 轮：token 更省，但更常换会话、重复注入 skill；
- 0：只靠闲置换会话，最省会话数，最费上下文。默认 20 偏「少建会话」；更在意 token
  就调到 5。

按一天算（只看分诊层，不含群聊天本身）：

- **0 个新群**：0 次分诊模型调用；sweep 仍按间隔拉 CLI，但没有个人 @ 就是 0 token。
- **0 个新群、sweep 在 1 个未值守群发现 @**：+1 次分诊（约 2.5–5k 输入），sweep 本身 0 token。
- **2 个新群、1 个 watch**：2 次分诊 + 1 次接手 ≈ 15–25k 输入、1–2k 输出。
- **20 个新群（`max_per_day` 上限）、5 个 watch、3 个 trial（trial 打开时）**：20 次分诊 +
  5 次接手 + 3 次复核 ≈ 0.3–0.8M 输入、10–30k 输出；实际取决于消息长度、是否复用值守台
  会话与缓存。如果 sweep 再命中 @，每个群加 1 次分诊，总数仍受 `max_per_day` 限制。
- **群轮询**：只花 CLI 调用，不花模型 token；只有 @ 你的群消息命中才唤醒群会话。

粗略公式：

```text
模型调用次数 ≈ 新群数 + sweep 命中的群数（合计 ≤ max_per_day）
              + 被决定 watch/trial 的群数 + trial 数
输入 token ≈ 分诊次数×1.5–3k + 值守台固定 1.5–2.5k + 值守台上下文累积
           + 接手轮×8–15k + 复核×1–3k
```

**成本旋钮**：`duty.enabled`、`max_per_day`、`max_groups`、`trial_hours`、
`session_max_turns`、`sweep_min`、`sweep_lookback_hours`。分诊只产生
`mention`，非 @ 的群消息不会唤醒群会话，这是最大的省钱点；`all` 不在分诊路径。
Feishu 每 10 分钟 1 条 `--is-at-me` 搜索（144 次/天）；DingTalk 每个未值守新群 144 次/天（3 个约 432 次、
10 个约 1440 次）。模型调用只在命中个人 @ 时发生；候选还要 1 次上下文探针 + 1 次成员数查询。

## 取舍

| 备选 | 否掉的理由 |
| --- | --- |
| 在插件里写规则（@ 就盯、大群不盯、关键词判断） | 判断需要群名语义、用户角色、历史偏好；规则会在 Node 与 prompt 里长两遍且互相打架。`AGENTS.md §设计铁律` 第 8 条把判断留给 agent。 |
| 新群一律自动 `timer=1` 盯 N 小时，不做判断 | 营销群、大群、临时群也会进轮询；成本不可控，且不是「自评价」。 |
| 分诊也允许选「全部消息」 | 用户明确要求新监听群一律 at 模式；全量群噪声与模型成本高，自动判断不该替用户开全量。要全量由用户手动改三态。 |
| 只在发现新群时看，不做 @ 清查 | 已存在的未值守群有人 @ 你，插件永远看不见；用户要求定期兜底。 |
| 每次清查连存量群一起扫 | 用户明确说已有群完全不用考虑；只扫基线之后的新群，存量群不读、不分诊。 |
| 清查也跑模型逐群判断 | 绝大多数群没有个人 @，跑模型纯浪费；sweep 只做 CLI 过滤，命中个人 @ 才起分诊。 |
| 依赖平台 mention feed / 推送 | 当前 adapter 没有稳定的「@我」feed；企微连会话枚举都没有。先做有限拉取，不假装实时。 |
| 清查发现 @ 也不重开已 `ignore` 的群 | 新的个人 @ 是新的信号；`ignore` 只对当时那条有效，`sweep_epoch` 保证同一条不重复。 |
| 每次新群都在面板问用户 | 用户不在时等于没有分诊；每个群一次点击，比现在的开关还重。 |
| 用平台事件（`lark-cli event consume`）做实时拉群 | 要另起长进程、另一套授权与重连；插件现在是纯拉取、零端口。真要做另开 ADR。 |
| 每个群用自己的会话做分诊 | 被 ignore 的群也会留下一个 DSH 会话，侧边栏被候选群塞满；跨群判断也不一致。 |
| 值守台长期不换会话，一个会话跑到底 | 判断是简单重复动作，上下文越积越长，缓存与费用都吃亏；`policy.md` + 最近 5 条判断已足够，按闲置 / `session_max_turns` 换新。 |
| 把值守台注册成用户工作区 / 放进项目仓库 | 污染工作区选择器，项目里多一个无关目录；判断不需要项目文件，独立私有 cwd 已经够。 |
| 把值守群也搬进值守台工作区 | 群工作要读项目上下文、写群工作本；搬走会丢上下文。值守台只判断，群工作留在原 workspace。 |
| duty 记录 / 未应用决策文件永久保留 | state 与磁盘随群数增长；`ignore`/`failed` 30 天、决策 7 天清理，`watch`/`trial` 保留即可。 |
| 插件删旧值守台 / 群会话 | DSH 没有删除会话接口；插件只解绑、不再使用，旧会话留在历史，由用户自行清理。 |
| 全局值守台 + HTTP / agent tool 写决策 | 插件没有稳定本地端口；DSH tool 注册不是本仓库的稳定契约。文件是 agent 本来就会写、插件可校验、可测试的通道。 |
| 让 agent 在分诊轮直接回 @ | 判断与对外发言混在一起：一次误判就变成全群可见的消息。分成「判断轮」与「接手轮」。 |
| 默认强制 24h trial | 用户要求两段式：新建判一次、之后只在新的个人 @ 时再判；默认 trial 关，避免每个新群多一次定时复核。要试用可显式打开。 |
| 允许无限 trial 续期 | 等于永久轮询，只是把决定拖后；一次试用，到期只能 watch / ignore。 |
| 决策写在 `state.json` 让 agent 直接改 | agent 没有事务写、容易和插件抢写；插件是唯一 writer，决策文件是窄接口。 |

## 风险与回滚

- 风险：探针把未值守群的最近 10 条消息交给 agent/模型，超出「用户本来没盯这个群」的预期。
  缓解：只 10 条、不下载媒体、不写日志、只进这一次 turn；总开关可关；面板显示判断理由。
- 风险：@ 清查会周期性读新群：Feishu 一条 `--is-at-me` 搜索可能带出已有群的 @；DingTalk
  逐新群拉取。缓解：按 `added_at > baseline_at` 过滤、`@all` 用 `isMention` 过滤、只读新群、
  不下载媒体/不写日志；`sweep_min=0` 可关；没有个人 @ 不跑模型。
- 风险：Feishu `--is-at-me` 返回 @all / 告警卡片，被误当个人 @。缓解：结果逐条
  `isMention`，`@everyone` / `@all` 不算；`@all` 不进分诊。
- 风险：群成员数查不到（DingTalk / WeCom / `truncations[]` / 查询失败）→ 自动路径只能
  ignore，用户觉得「为什么不自动开」。缓解：这是有意的保守硬门；面板显示「人数未知，
  只能手动」；手动 `/api/watch` 可强制。
- 风险：sweep 只覆盖基线之后的新群 + 24h，新群没被发现或 @ 更早时漏掉。缓解：面板可手动
  「让分身判断」；这是兜底不是全量审计，spec 已写明。
- 风险：已 `ignore` 的新群被新的 @ 反复触发分诊，产生噪声/成本。缓解：`sweep_epoch` 保证同
  一条 @ 只触发一次；用户可 block 该群、调大 `sweep_min`，或关 sweep。
- 风险：sweep 的 fetch 失败/限流，导致本轮漏扫。缓解：单群失败跳过、记日志、下一 sweep
  重试；不阻塞正常轮询；`last_sweep_at` 仍推进，面板可见。
- 风险：sweep 与正常水位互相污染，已经处理的 @ 被当新事件。缓解：sweep 用独立
  `duty.sweep_epoch`，不写 `last_sync`/`recent`/正常水位；`watch`/`trial`/`ignore` 应用时
  把 `sweep_epoch` 推到当前 `last_epoch`。
- 风险：每个新群一次模型调用，批量入群时成本可见。缓解：每日配额、值守群上限、一次
  tick 一个、首次基线不排队；配额用完不丢事件但也不烧钱。
- 风险：agent 误判盯了不该盯的群。缓解：默认 `mention`、trial 开时可选、面板可推翻、上限；
  分诊轮不发言，误判不会立刻变成对外消息。
- 风险：发现延迟 10 分钟，@ 可能已经冷掉。这是拉取模型的固有代价；本次不改成推送。
  需要更快时另开 ADR。
- 风险：值守台被用户占用或在飞长任务，分诊排队。缓解：不打断、下一 tick 重试、超过 24h
  记 stale；面板显示队列。
- 风险：值守台 cwd 被改/目录被删，决策文件写不进去。缓解：解析时校验 cwd 不符就重开；
  目录由插件 0700 重建；写失败记 `duty.error` 并让面板可重试。
- 风险：旧值守台/群会话留在 DSH 历史，侧边栏会话数仍会增长；DSH 没有删除接口，插件只能
  换绑、不再使用。缓解：值守台全局一个 + `duty.session_max_turns` 轮换 + `duty.max_groups`
  限制同时值守群；旧会话由用户在 DSH 里自行清理，面板只展示当前绑定。
- 风险：`duty.record_keep_days` 清掉旧的 `ignore` 理由，用户之后看不到当时为什么没盯。
  缓解：只清 `ignore` / `failed`，`watch` / `trial` 保留；详情仍可手动重新判断，清理本身
  不会重排队；新的个人 @ 仍可由 sweep 触发。
- 风险：决策文件与插件竞态（agent 写一半、进程重启）。缓解：turn 结束后再读、JSON 校验、
  `event_id` 幂等、重启时 `triaging→queued`、应用前重取 chat。
- 回滚：设置页关 `duty.enabled`（停自动分诊/清查；已排队等重开、试用到期自动结束），
  或只把 `sweep_min=0` 关清查（不影响新群分诊），或回退相关 commit。`chats[].duty` / `desk`
  是纯增量，旧代码加载时忽略；`<state.dir>/duty/` 可手动删除，不影响 `state.json` 与已有值守。
